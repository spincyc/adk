# Inert cue scheduling and audit

Status: **host verified; hardware acceptance open**  
Energy class: **E1** — USB-powered Mega, passive buttons, and resistor-limited LEDs  
Safety boundary: **learner-operated visual intervals only**

This lesson turns a caller-owned plan and explicit operator input into a stable
snapshot and bounded replay record:

`plan + supplied time + review/confirm → snapshot → inert LEDs + audit`

Cue IDs are opaque visual labels. They are not pins, addresses, frequencies,
launcher channels, or permission to act. The core owns no hardware and exposes
no callback or generic output seam.

## Exact circuit and budget

| Role | Mega pins | Connection |
|---|---|---|
| Cue indicators / Lesson 029 TP29 | D22–D29 | each pin → 1 kΩ → LED anode; cathode → GND |
| Review, Run, Confirm, Skip, Cancel | D30–D34 | momentary switch to GND; internal pull-up |
| Common-cathode RGB state indicator | D5–D7 | one 1 kΩ resistor per red, green, and blue channel |

The sketch drives at most one cue channel and one RGB channel at a time.
Using the deliberately conservative zero-forward-voltage calculation, a 5.0 V
rail and 1 kΩ resistor bound each active LED channel to 5 mA and the two-channel
LED load to 10 mA. This design bound is not a physical measurement.

TP29 is the Mega-pin side of the selected cue resistor, measured relative to
Mega GND. The supported circuit contains no relay, transistor-driven load,
initiator, launcher connector, radio, captured protocol, or external equipment.

## Plan and lifecycle

`InertCueSchedulerConfig` copies a fixed plan of 1–32 cues and a nonzero
confirmation window. A valid plan has unique IDs from 0–31, strictly increasing
offsets, nonzero visible durations, no overlap, and an unambiguous 32-bit end.
Offsets remain relative to the accepted Run request; confirmation delay never
shifts later cues.

Objects are constructed in dependency order:

```cpp
CueAuditEntry auditStorage[64];
CueAuditBuffer audit(auditStorage, 64);
InertCueScheduler scheduler(config, audit);
```

`scheduler.initialize()` validates the copied configuration, initializes the
empty caller-owned audit, records `Initialized`, and enters Idle. Scheduler
shutdown records `Shutdown` and preserves the ledger. Audit-buffer shutdown
then clears it.

## Operator contract

`reviewHeld` is a level. Run, Confirm, Skip, and Cancel are debounced edge
events. More than one non-cancel edge in one sample is invalid. Cancel has
absolute priority.

1. Hold Review to enter Review.
2. Press Run once to establish the plan epoch.
3. Inspect the named next cue during Confirmation.
4. Press Confirm inside the inclusive confirmation window.

Releasing Review from a running phase blanks the cue and enters Held. Restoring
Review alone does not resume; press Run once. A cue interrupted while Active is
not resumed mid-interval. Skip is valid only during Confirmation. Expired
confirmation is recorded as `Timeout`.

## Three dependent wins

The opening journey advances only in order:

1. Hold Review and observe the steady blue Review state.
2. While Review remains held, press Run and observe the first cue enter
   Confirmation with the fast red cadence.
3. While that confirmation remains open, press Confirm and observe only cue
   LED index 0 with the steady green state.

Run before Review and Confirm before an open confirmation cannot unlock a
later win. The first two wins keep every cue output inactive; the third depends
on both earlier transitions and exposes one inert indicator. The panel always
shuts down two minutes after startup, independent of every button.

The scheduler accepts at most one changed input frame per supplied timestamp.
Repeating the identical frame is idempotent; changing it at the same timestamp
is `InvalidArgument`. The Mega sketch therefore samples once per distinct
`millis()` tick.

## Snapshot presentation

Phase is authoritative. `hasCue` names a current or next cue in Waiting,
Confirmation, and Active, but a cue LED is permitted only for
`phase == Active && hasCue`.

| Phase | Cue LEDs | RGB evidence |
|---|---|---|
| Idle / Review | all off | steady blue |
| Waiting | all off | short blue pulse |
| Confirmation | all off | fast red pulse |
| Active | exactly `cueIndex` | steady green |
| Held | all off | slow blue pulse |
| Complete | all off | steady green |
| Cancelled / Fault | all off | steady red |
| shutdown | all released | off |

Color is supporting evidence; the cue lamps, cadence, phase name, and TP29
procedure keep interpretation from depending on color alone. Serial output is
optional and never drives a decision.

## Bounded audit and stable text

The audit is append-only caller storage, not an overwriting ring. Capacity
exhaustion enters Held with `CapacityExceeded` so operation cannot continue
unrecorded. Events are:

`initialized`, `review-started`, `run-requested`,
`confirmation-requested`, `confirmed`, `cue-shown`, `cue-hidden`,
`cue-skipped`, `held`, `resumed`, `cancelled`, `faulted`, `completed`, and
`shutdown`.

`CueAuditEncoder` writes atomically, adds a newline but no NUL byte, and requires
at most 96 bytes:

```text
adk-cue,1,<sequence>,<ticks>,<event>,<cue-or-dash>,<index-or-dash>,<status>
```

Absent cue and index fields are `-,-`. The public status vocabulary includes
`ok`, `invalid-argument`, `invalid-configuration`, `resource-busy`,
`not-initialized`, `capacity-exceeded`, `timeout`, and `internal-invariant`.

## Narrative sketch

```cpp
observeOperator    (now);
decideCueSchedule  (now);
presentCueSnapshot (now);
```

Setup acquires all five buttons, eight cue LEDs, the RGB indicator, and the
scheduler; configures every output inactive; then starts the panel. The loop
observes one complete input frame, updates once, and presents one stable
snapshot. Cue IDs such as 3, 7, 12, and 29 never index pins; `cueIndex` selects
the canonical display position.

## Predict, observe, interpret

1. Unpowered, verify one 1 kΩ resistor per LED channel, common-cathode RGB
   polarity, five switch-to-GND paths, and no external-load connection.
2. Predict blue acquisition evidence only after every owner initializes.
3. Hold Review, press Run, and predict TP29 remains inactive through
   Confirmation.
4. Confirm once; predict only the selected cue output becomes active for
   `[confirmedAt, confirmedAt + visibleFor)`.
5. Observe TP29 and the selected LED, then interpret agreement only as evidence
   for snapshot-to-inert-display mapping.
6. Release Review while Active and verify cue output blanks before resuming.
7. Leave the buttons untouched and observe immediate darkness and released
   indicator endpoints at the fixed two-minute ending; then remove USB power.

A dark LED and inactive voltage do not by themselves prove high impedance.
Resource release is separately covered by deterministic ownership tests; a
physical high-impedance claim needs an explicit weak-pull fixture or instrument
method. Physical acceptance remains open outside this learner artifact.

Stop and remove USB power for a hot part, unstable supply, wrong polarity,
missing resistor, unexpected indicator, out-of-rail TP29, or any disagreement
between the authoritative pin table and the breadboard. Confirmation is an
instructional input, not a safety interlock.

Compilation, deterministic tests, and the PDF are software evidence. They are
not physical acceptance.
