# Reviewed inert show-cue simulator

Status: **host verified; physical acceptance open**  
Energy class: **E1** — USB-powered Mega, passive switches, and
resistor-limited LEDs  
Safety boundary: **synthetic observations and inert visual cues only**

Lesson 030 composes the synthetic channel assessment from Lesson 028 with the
reviewed cue scheduler and bounded audit from Lesson 029:

`complete synthetic frame → assessed channel → evidence gate → reviewed cue → inert LED + audit`

The result is an educational simulator. A cue ID is an opaque display label,
not a pin, channel, address, protocol field, firing order, or permission to
act. The core has no callback, generic output adapter, radio path, external
load interface, or heap allocation. Do not connect this project to a relay,
transistor-driven load, initiator, commercial show connector, antenna, or
unknown equipment. Removing USB power is the physical stop.

## Exact starter circuit and budget

| Role | Mega pins | Connection |
|---|---|---|
| Eight inert cue indicators / TP29 | D22–D29 | each pin → 1 kΩ → LED anode; cathode → GND |
| Review, Run, Confirm, Skip, Cancel | D30–D34 | momentary switch to GND; internal pull-up |
| Synthetic observation editor / TP28 | D35–D38 | momentary switch to GND; internal pull-up |
| Common-cathode RGB state indicator | D5–D7 | one 1 kΩ resistor per red, green, and blue channel |

The sketch drives at most one cue LED and one RGB channel at a time. With the
deliberately conservative zero-forward-voltage calculation, 5.0 V through
1 kΩ bounds each active channel to 5 mA and the combined LED load to 10 mA.
This calculation is not a measurement; the open bench card still requires the
actual rail, resistor, and LED forward-voltage readings.

TP28 is the selected synthetic input switch pin, measured relative to Mega
GND. TP29 is the Mega-pin side of the selected cue LED resistor, also relative
to GND. The pin table and canonical sketch are authoritative. Serial is
optional supporting evidence and is never the only observation path.

## Composition and explicit mapping

The simulator copies a `InertCueChannelMap` indexed by plan position. Its count
must equal the scheduler cue count, and each mapped channel must be in the
assessor's 0–7 range. Cue IDs are deliberately different from channel IDs in
the canonical plan:

| Plan index | Opaque cue ID | Assessed channel |
|---:|---:|---:|
| 0 | 3 | 5 |
| 1 | 7 | 2 |
| 2 | 12 | 7 |
| 3 | 29 | 0 |

The mapping is data, never an inference from a cue ID.

Objects are constructed in dependency order: runtime, buttons, cue LEDs, RGB
indicator, assessor, audit storage, scheduler, then simulator. Construction is
inert. `initialize()` starts the assessor and then the scheduler; rollback is
reverse order. `shutdown()` first stops the scheduler and guarantees no
visible cue, then stops the assessor. It leaves the scheduler-owned audit
session readable. Repeated shutdown and destruction are safe.

The simulator borrows the assessor, scheduler, and audit; they must outlive it.
It consumes an input frame synchronously and retains no observation pointer.

## Complete-frame transaction

Every call supplies exactly eight observations with unique channel IDs 0–7,
one common timestamp, and one operator frame. Input order is canonicalized by
channel. Null storage, a wrong count, duplicate or invalid channels, invalid
observation values, ambiguous time, or a changed frame at the same timestamp
is rejected without exposing a partial observation.

An identical complete frame repeated at the same timestamp is idempotent. The
accepted-frame precedence is:

1. Cancel.
2. Invalid non-cancel operator chord.
3. Selected-channel evidence fault or hold.
4. Review release.
5. Phase-specific operator action.
6. Timed transition.

This order is deterministic replay behavior, not a functional-safety claim.
No error path is allowed to expose a cue LED.

## Evidence gate

The scheduler remains the sole writer of cue-audit entries. The simulator
derives only a channel-agnostic `Permit`, `Hold`, or `Fault` gate for the cue at
the current plan index.

| Selected assessment | Gate | Result |
|---|---|---|
| Closed | Permit | operator may confirm; scheduler alone decides visibility |
| Open | Hold | cue off; fresh evidence and renewed review required |
| ShortSimulated | Hold | cue off; fresh evidence and renewed review required |
| Stale | Hold | cue off until a fresh complete frame |
| Unavailable | Hold | cue off until a fresh complete frame |
| Contradictory | Fault | latched simulator fault; every cue off |

Recovery never resumes an interrupted cue automatically. The operator must
restore Review and make a fresh phase-appropriate request and confirmation.
Cancel and latched faults require reinitialization.

## Public values

`InertShowSnapshot` contains the composed state and fault, the selected channel
assessment when one exists, the complete nested scheduler snapshot, the audit
sequence, a trace digest, and a `Status`.

| Show state | Narrow meaning | Visible evidence |
|---|---|---|
| Startup | coordinator inactive | all outputs off |
| Review | operator review gate established | steady blue |
| Ready | a cue is pending but not visible | short blue cadence |
| Running | scheduler is progressing | phase-specific cue/RGB evidence |
| Held | evidence or review gate prevents progress | cue off; slow blue cadence |
| Complete | every planned cue resolved | cue off; steady green |
| Cancelled | terminal operator cancellation | cue off; steady red |
| Fault | contradictory or invalid state | cue off; red fault cadence |

`InertShowFault` distinguishes `None`, `ObservationContradictory`,
`AuditFull`, `InvalidInput`, and `InternalInvariant`. Open, short-simulated,
stale, and unavailable assessments are nonterminal holds rather than faults.
The nested scheduler phase remains authoritative for whether a cue is visible:
only `Active && hasCue` permits exactly one cue indicator.

## Narrative sketch

The canonical loop preserves the observe, decide, actuate vocabulary while
making one atomic simulator update:

```cpp
void loop ()
{
    const adk::TimePoint now (millis ());

    readSimulatorInput (now);
    updateSimulator    (now);
    showInertCues      ();
    showSimulatorState (now);
}
```

The input builder always supplies all eight synthetic observations.
`showInertCues()` can address only the eight statically constructed
`MonoLed` objects. It consumes a snapshot and cannot call back into the core.

## Replay and bounded audit

The version-one trace starts with:

```text
adk-inert-show-trace,1
```

Each following row contains supplied ticks, one synthetic observation token,
and the Review, Run, Confirm, Skip, and Cancel bits. The public fixture tokens
are `C` (closed pair), `O` (open pair), `S` (short-simulated pair), `U`
(unavailable pair), and `X` (contradictory pair). They describe only ADK-owned
synthetic values; the format has no pin map, waveform, radio data, or external
protocol field.

Replay emits stable `adk-show,1,...` snapshots. Audit mode emits the Lesson 029
`adk-cue,1,...` ledger written solely by the scheduler. `traceDigest` detects
accidental replay corruption; it is neither cryptographic authentication nor
proof that a physical circuit matched the trace.

```sh
make inert-show-test
make inert-show-replay
make inert-show-replay TRACE=tests/fixtures/inert_show_happy.trace
make inert-show-audit TRACE=tests/fixtures/inert_show_happy.trace
```

These targets require neither an Arduino nor a network.

## Predict, observe, interpret

1. With USB disconnected, verify one 1 kΩ resistor for each LED channel,
   common-cathode RGB polarity, all switch-to-GND paths, and no external-load
   connection.
2. Predict the startup sweep. Observe every cue indicator individually, then
   interpret it only as endpoint-acquisition and cue-to-indicator evidence.
3. Select mapped channel 5 for cue ID 3. Predict the TP28 level before pressing
   its synthetic input control; measure relative to Mega GND.
4. Present a complete Closed frame, hold Review, and press Run. Predict TP29
   remains inactive while confirmation is pending.
5. Confirm inside the inclusive window. Observe the selected cue LED and TP29,
   and reconcile their interval with the scheduler snapshot and audit entry.
6. Repeat with Open, ShortSimulated, Stale, and Unavailable. Predict a hold
   with every cue output inactive; then provide a fresh Closed frame and renew
   review and confirmation.
7. Supply a contradictory pair. Predict a latched fault, red fault cadence,
   inactive TP29, and no automatic recovery.
8. Invoke shutdown separately. Record immediate darkness and the electrical
   state at TP29, then remove USB power.

The evidence chain is:

`TP28 level → synthetic observation → assessment → reviewed schedule decision → TP29 voltage → audit entry`

Agreement at one link does not prove the next. A lit LED proves only the
simulator's inert presentation. It proves nothing about an external load,
radio, real channel, show readiness, or functional safety. A dark LED and an
inactive voltage do not alone prove high impedance. Resource release requires
a separate instrument method; without it, record that claim as open.

Stop and remove USB power for a hot part, unstable supply, wrong polarity,
missing resistor, unexpected indicator, an out-of-rail TP28 or TP29 reading,
or any disagreement between the pin table and breadboard. The bench record
must name the exact board, parts, measured rail and resistors, instruments,
tool versions, commit, predictions, observations, deviations, operator, and
date. Compilation and deterministic replay are software evidence, not
physical acceptance.
