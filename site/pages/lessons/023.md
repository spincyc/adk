# Inert load interlock

Status: **host verified; physical acceptance open**
Primary experiment: **E1** — USB-powered Mega and resistor-limited LEDs only
Excluded hardware: **relays, motors, pumps, heaters, external load supplies, and mains**

Lesson 023 turns a choice among fan, pump, heater, and none into one bounded,
observable intent:

`PowerDomain admission → InertLoadInterlock policy → InertLoadPanel → three LEDs`

The words *fan*, *pump*, and *heater* name simulated channels. In the supported
circuit every channel is only a resistor-limited LED. The software interface is
not evidence that a real load is powered safely, and it is not a functional
safety controller.

## Three facts, three observations

Keep these facts separate:

| Fact | Public evidence | Circuit evidence | What it does not prove |
|---|---|---|---|
| Requested | `snapshot.requested` | D13 request pulse | admission or application |
| Applied | `snapshot.active` | exactly one of D38/D40/D41 | real load power |
| Faulted | `snapshot.status` is not `ok()` | D12 latches on | physical isolation |

Command admission is a software policy fact. It is not electrical power
evidence. An illuminated D38, D40, or D41 proves only that the corresponding
indicator circuit was commanded and visibly responded.

## Supported inert circuit

| Meaning | Mega pin | Connection |
|---|---:|---|
| Requested-intent pulse | D13 | built-in LED |
| Applied pump | D38 | D38 → 220 Ω → LED anode; cathode → GND |
| Applied fan | D40 | D40 → 220 Ω → LED anode; cathode → GND |
| Applied heater | D41 | D41 → 220 Ω → LED anode; cathode → GND |
| Latched fault | D12 | D12 → 1 kΩ → LED anode; cathode → GND |

Remove USB power before making or changing a connection. Leave every relay
module, motor, pump, heater, transistor board, and external supply disconnected.
Stop on a hot part, unstable USB connection, unexpected simultaneous applied
indicators, or disagreement between the table and breadboard.

## Intent is not actuation

`InertLoadInterlock` owns no output pin. It remembers a requested load, admits
at most one active intent, and fails closed when its borrowed `PowerDomain`
revokes command admission. A fault is sticky: restoring admission alone does
not reactivate anything. Recovery requires an explicit lifecycle restart.

Each `IndicatorPump` owns one indicator endpoint. `InertLoadPanel` borrows the
three outputs in fan, pump, heater order; therefore the panel cannot outlive
them. Its transition is break-before-make: it clears the prior indicator before
applying a different one. Any endpoint failure makes one best-effort all-off
pass and reports the complete `Status`.

The focused `IndicatorPump` adapter exposes only `Off` and `On`; its “pump” is
still one LED. `PanelPumpOutput` borrows the panel and adapts only its pump
channel for `WateringController` in Lesson 024. Those borrowed relationships
must not outlive the panel. None of these names authorizes connection to an
energetic device.

## Narrative loop

The canonical Mega sketch follows the same words as the circuit:

1. **Observe** elapsed time and the current snapshot.
2. **Decide** which inert channel to request next.
3. **Actuate** the panel and render requested, applied, or fault evidence.

Pass a complete failure value to the observation boundary:

```cpp
const adk::Status status = interlock.select (requestedLoad);

if (!status.ok ())
{
    observeFailure (status);
}
```

`status.transient()` classifies the cause; it does not authorize an automatic
retry. An invalid enum value leaves the prior valid selection unchanged.
Revoked admission removes active intent and records `HardwareFailure`.

## Predict, observe, interpret

### Normal sequence

- **Predict:** D13 pulses first; then exactly one applied LED changes.
- **Observe:** watch D13 and D38/D40/D41 without Serial.
- **Interpret:** the ordering supports request-before-application and mutual
  exclusion in this inert circuit.

### Admission fault

- **Predict:** after admission is revoked, requested intent may be recorded,
  every applied LED is off, and D12 latches.
- **Observe:** compare D13, the three applied LEDs, and D12.
- **Interpret:** the disagreement is deliberate fault evidence. It proves the
  software policy failed closed; it does not prove power isolation.

### Shutdown

- **Predict:** all applied indicators become inactive before their pins are
  released.
- **Observe:** check the LED state, then measure D38/D40/D41 relative to the
  named GND point after shutdown.
- **Interpret:** darkness supports inactive semantic state; a high-impedance
  measurement is separate safe-state evidence.

## Deterministic host proof

Host tests cover construction, idempotent lifecycle, every selection
transition, invalid selection, asynchronous admission revocation, sticky
faults, explicit recovery, output failure, rollback, destruction, and the
invariant that no trace contains two active simulated loads.

Run the repository-owned workflow:

```sh
make host-test
make arduino-Lesson023InertLoadInterlock
make size-Lesson023InertLoadInterlock
make lessons
make lessons-check
make site-check
```

Compilation and host replay are not physical verification. The PDF companion
contains the full prediction worksheet, fault laboratory, exercises, and a
blank physical acceptance record.
