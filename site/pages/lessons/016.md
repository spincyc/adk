# 4×3 matrix keypad

Status: **host verified; hardware acceptance open**  
Energy class: **E1** — USB-powered Mega 2560 and passive membrane keypad

This lesson separates electrical scanning from operator-event interpretation:

`4×3 matrix → MatrixKeypad scan → KeypadSample → Keypad → KeypadSnapshot`

`MatrixKeypad` transactionally owns seven pins, performs one bounded four-row
scan for each `update(now)`, and composes the hardware-independent `Keypad`
interpreter. `Keypad` debounces the supplied sample, maps the twelve positions,
and requires a complete release before another press can be accepted. A
multi-key result is `InvalidChord`; it never becomes a digit as fingers lift.

This is an operator-input exercise, not an access-control or security
interface.

## Parts

- Arduino Mega 2560
- passive 4×3 membrane matrix keypad
- USB cable
- logic probe or oscilloscope for TP-R0/D22; a multimeter is not fast enough
  to characterize the scan pulse
- optional continuity tester for identifying an undocumented keypad tail

Do not assume the printed tail order. Identify the four rows and three columns
from manufacturer documentation or with an **unpowered** continuity test. No
keypad conductor connects directly to 5 V or GND.

## Wiring

| Signal | Mega pin | Keypad position |
|---|---:|---|
| `Row0` / TP-R0 | D22 | row containing 1, 2, 3 |
| `Row1` / TP-R1 | D23 | row containing 4, 5, 6 |
| `Row2` / TP-R2 | D24 | row containing 7, 8, 9 |
| `Row3` / TP-R3 | D25 | row containing `*`, 0, `#` |
| `Column0` | D26 | column containing 1, 4, 7, `*` |
| `Column1` | D27 | column containing 2, 5, 8, 0 |
| `Column2` | D28 | column containing 3, 6, 9, `#` |
| `OperatorEvidence` | D13 | built-in LED; no external connection |

During a scan, one row is briefly driven low while the three columns are read
with internal pull-ups. Every inactive row is an input, not a driven-high
output. After `shutdown()`, all seven keypad pins return to input/high-impedance
state and their claims are released.

## Public operations

| Operation | Contract |
|---|---|
| `initialize()` | Validate seven distinct pins, initialize interpretation, acquire all claims, then configure scanning |
| `update(now)` | Scan once and advance debounce using caller-supplied time |
| `snapshot()` | Report the stable key, state, status, raw mask, and press/release events |
| `shutdown()` | Stop scanning, return pins to input state, release claims, and reset interpretation |
| destructor | Perform `shutdown()` without throwing |

Construction is inert. Initialization and shutdown are idempotent. Failed
validation or acquisition produces no scan and retains no claim.

`KeypadSnapshot.state` is `Released`, `Pressed`, `InvalidChord`, or `Fault`.
`pressEvent` and `releaseEvent` describe the transition accepted by the latest
update; they are observations, not callbacks. A diode-less matrix cannot
reliably identify arbitrary simultaneous keys, so every multi-bit result is
rejected.

## Predict, observe, interpret

Before powering the circuit, predict that TP-R0 has no scan activity before
successful acquisition. Attach the probe to D22 and Mega GND while power is
off, inspect the connections, then restore USB power.

After initialization, observe one bounded low selection pulse at TP-R0 during
each scan. The D13 evidence pattern reports interpretation independently:

| Observation | D13 pattern |
|---|---|
| Ready and released | one startup pulse, then off |
| Accepted digit | one through ten short pulses |
| Accepted `*` | one long pulse |
| Accepted `#` | two long pulses |
| Invalid chord | repeating paired short pulses until full release |
| Scan or update fault | repeating three-short pattern |

Interpret TP-R0 activity as evidence that scanning began after resource
acquisition. Interpret D13 as evidence of the accepted operator event. Neither
proves safe shutdown.

For safe-state evidence, invoke the shutdown exercise and verify that TP-R0
pulses stop. The host recording driver separately verifies that D22–D28 return
to input state and that all claims can be reacquired. An extinguished D13 alone
does not prove either condition.

## CLI workflow

```sh
make host-test
make arduino-Lesson016MatrixKeypad
make size-check
make lessons
make lessons-check
make site
make site-check
```

The deterministic host traces cover debounce boundaries, held keys, complete
release gating, invalid chords, faults, timestamp wraparound, acquisition
rollback, scan order, repeated lifecycle calls, destruction while active, and
replay. A successful host test or Mega compile is not physical verification.
The firmware-size baseline and bench observations must be recorded before
promotion.

The printable lesson complements this page with the black-and-white schematic,
pencil orientation drawing, timing and state diagrams, replay worksheets,
troubleshooting tree, and blank bench record. This page remains the concise,
searchable API and wiring reference.

## Deferred work

Hardware acceptance remains open until a selected keypad's tail order, TP-R0
waveform, all twelve keys, chord response, reset, shutdown, and resource reuse
are observed and recorded on a Mega 2560. The injected scan transport already
distinguishes a driver failure from an ordinary released sample in host tests.

A 4×4 keypad is explicitly deferred. It requires an eighth claim, a caller
supplied 16-entry key map, separate ghosting and rollback tests, another
example, a measured size budget, and its own bench evidence. It will not change
this lesson's 4×3 pinout or fixed twelve-key mapping.
