# Lesson 064 — bounded copied 1-Wire transactions

Status: **Host verified and published at E0; exact powered
single-wire endpoint, specimens, timing, and bench acceptance open**

Energy class: **E0 copied values and semantic line intent only**
Safety boundary: **no GPIO pin, endpoint, resource claim, timer, interrupt,
bus, pull-up, strong-pull-up switch, supply, probe, clock, or powered circuit**

`OneWireTransactionPolicy` expands one closed, typed operation into a bounded
sequence of line intents and validates copied receipts:

`typed request + supplied microsecond time + copied line receipts → attributed transaction snapshot`

It is not a hardware `OneWireBus`. `DriveLow`, `Release`, and `Sample` are
semantic values; the policy cannot move or observe a physical line. A future
E1 adapter must separately own the endpoint and timing resources and prove
that it executed those intents.

## A deliberately closed operation set

Lesson 064 permits only these reviewed operations:

| Operation | E0 meaning |
|---|---|
| `ResetPresence` | expand one copied reset/release/presence sequence |
| `SearchRomPass` | perform one bounded copied search pass from fixed search state |
| `ReadRomSingleDrop` | read one copied ROM only when configuration explicitly says single-drop |
| `MatchRomReadPowerSupply` | address one nonzero ROM and copy one supply-status result bit |
| `MatchRomStartConversion` | address one nonzero ROM and emit the typed conversion request sequence |
| `MatchRomReadConversionStatus` | continue the immediately preceding completed conversion-start transaction for the same ROM and copy exactly one status bit |
| `MatchRomReadScratchpad` | address one nonzero ROM and copy at most nine returned bytes |

The API accepts no arbitrary opcode, captured pulse train, script, unknown
protocol replay, EEPROM-copy command, or unbounded polling instruction.
Adding an operation is a new architecture and safety review boundary.

Lesson 064 rejects only an all-zero addressed ROM. Any other complete 64-bit
value—including all ones, a wrong family byte, or a bad CRC—is transported
byte-for-byte without interpretation. Lesson 065 alone qualifies family
`0x28`, ROM CRC, scratchpad CRC, resolution, conversion freshness, and
temperature.

`ReadRomSingleDrop` rejects a multidrop configuration. `SearchRomPass` owns
only one bounded branch/pass and returns fixed copied search state; the caller
schedules another operation after the current transaction and cleanup are
complete. Enumeration order has no spatial meaning.

Every ordinary operation begins with reset and presence. `ResetPresence`
stops after that sequence without sending a command. The sole reset exception
is `MatchRomReadConversionStatus`: it is admitted only as a one-slot
continuation of this policy's immediately preceding completed
`MatchRomStartConversion` for the same nonzero ROM. A free-standing status
request rejects atomically.

## Public transaction values

`OneWireOperationRequest` freezes:

- nonzero request sequence;
- one closed operation;
- complete addressed ROM or fixed search state;
- supplied microsecond start time;
- explicit supply mode; and
- producer `Status`.

`OneWireStepIntent` binds owner token, lifecycle generation, configuration
revision, request sequence, transaction generation, operation, phase,
phase sequence, slot index, write bit, line intent, sample requirement,
earliest/latest legal action time, and addressed ROM.

`OneWireStepReceipt` carries producer source and configuration, receipt
sequence and observation time, then repeats the intent's owner, lifecycle,
request, transaction, operation, phase, phase-sequence, slot, and applied-line
correlation. It adds the copied sampled level, acceptance bit, and producer
status. Fields such as the addressed ROM and legal window remain in the
policy's owed intent; they are checked through that bound correlation rather
than copied into the receipt.

`OneWireTransactionSnapshot` retains the frozen request, operation, phase,
quality, search result, returned ROM, at most nine copied bytes, accepted
prefix length, presence evidence, release requested/confirmed state,
completion time, and status. Partial bytes remain attributable prefix
evidence; they never become a completed device response.

Large output values are caller-owned. The published lifecycle is:

```cpp
Status initialize (
    MicrosecondTimePoint now,
    OneWireStepIntent&   releaseIntent) noexcept;

Status begin (
    MicrosecondTimePoint           now,
    const OneWireOperationRequest& request,
    OneWireStepIntent&             intent) noexcept;

Status update (
    MicrosecondTimePoint       now,
    const OneWireStepReceipt&  receipt,
    OneWireStepIntent&         intent) noexcept;

Status advance (
    MicrosecondTimePoint now,
    OneWireStepIntent&   intent) noexcept;

Status cancel (
    MicrosecondTimePoint now,
    OneWireStepIntent&   intent) noexcept;

Status reset (
    MicrosecondTimePoint now,
    OneWireStepIntent&   releaseIntent) noexcept;

Status shutdown (
    MicrosecondTimePoint now,
    OneWireStepIntent&   releaseIntent) noexcept;

Status confirmCleanup (
    MicrosecondTimePoint      now,
    const OneWireStepReceipt& receipt) noexcept;

Status snapshot (
    OneWireTransactionSnapshot& snapshot) const noexcept;

Status completedEvidence (
    OneWireTransactionSnapshot& evidence) const noexcept;

bool initialized () const noexcept;
```

Construction is inert. The policy is non-copyable and non-movable, owns fixed
storage, retains no caller pointer, allocates no heap memory, invokes no
callback, and reads no hidden clock.

## Microsecond windows without delay loops

The transaction model uses a dedicated unsigned 32-bit microsecond time
domain. Millisecond `TimePoint` cannot represent the copied slot evidence.
Configuration fixes independent lower and upper windows for:

- reset-low duration;
- reset release;
- presence start and presence-low duration;
- write-zero and write-one low duration;
- read initiation and read sample;
- complete slot duration and recovery; and
- the overall transaction deadline.

Every required duration is nonzero, ordered, and below the modular half range.
No window is inferred by subtracting another duration. Host tests exercise one
unit below, both inclusive boundaries, and one unit above every window.

No service call sleeps, delays, polls, retries, or catches up. A matching
receipt advances at most one phase or slot and emits at most one next intent.
Bits and bytes are serialized least-significant first.

`MatchRomReadConversionStatus` performs exactly one copied read slot after the
same policy has completed `MatchRomStartConversion` for the same ROM. A low or
high result is transaction evidence, not a transport failure. The policy never
loops until conversion completes. A later status check requires another
completed conversion-start transaction; status reads cannot be chained.

a folder, representing least-significant first slot order and an

## Presence and search evidence

Every non-continuation transaction begins with the typed reset, release, and
presence sequence required by its operation. The one-slot conversion-status
continuation uses the immediately preceding completed conversion-start
evidence instead. `NoPresence` remains a domain outcome. It is not rewritten
as a zero ROM or a cold temperature.

A Search ROM pass retains the complete fixed ROM accumulator,
`lastDiscrepancy`, and `lastDevice` state. At each search bit, the two copied
read slots distinguish:

| ID bit | complement bit | Meaning |
|---:|---:|---|
| 0 | 1 | all participating devices have zero |
| 1 | 0 | all participating devices have one |
| 0 | 0 | collision; choose the bounded branch fixed by search state |
| 1 | 1 | no participating device; fault the pass |

One pass returns at most one ROM and next search state. The policy does not
grow a device list, assign physical positions, qualify CRC, or conclude that a
missing later search result proves physical disconnection.

## Keep physical external-power evidence open

`ExternallyPowered` is the only admitted copied `supplyMode` value; admitting
that enum does not energize or qualify a circuit. A `ParasitePower` request
returns `Unsupported` before mutation.

There is no strong-pull-up phase or line intent. `Release` can never be
reinterpreted as output-high drive, sufficient weak pull-up, or conversion
power. The DS18B20 primary specification requires a distinct strong-pull-up
path and exclusive bus hold for parasite-powered conversion; implementing
that capability requires a separate powered-endpoint stress pass and E1b
acceptance.

Lesson 064 also omits scratchpad-to-EEPROM copying. It therefore makes no
nonvolatile-write, endurance, strong-pull-up, or persistence claim.

## Atomic receipt correlation

Structural validation precedes phase meaning. A receipt must match:

- expected producer source and configuration;
- owner, lifecycle, and policy configuration;
- request and transaction generation;
- operation;
- phase and phase sequence;
- slot index and applied line intent; and
- its legal microsecond window.

The addressed ROM is not a receipt field. It remains frozen in the bound
request and owed intent. Conversion-status admission compares the new request
against the same policy's immediately preceding completed conversion-start
request, including exact ROM identity.

A foreign, crossed, malformed, or fieldwise changed duplicate rejects
atomically. A structurally matching receipt outside its inclusive phase
window is different: it is retained as attributed timeout evidence and starts
one release rollback. It cannot advance the requested operation.

At equal receipt sequence and observation time, only a byte-identical complete
receipt is idempotent. A duplicate never advances a bit, phase, prefix, or
deadline. Forward sequence and time use modular half-range rules. Regression,
backward time, exact-half-range ambiguity, and lifecycle crossing reject
atomically. If accepting a call could not leave a unique next transaction,
phase, lifecycle, receipt, or cleanup correlation, the entire call returns
`CapacityExceeded` without mutation; no sequence or generation wraps to zero.

A structurally valid producer failure remains attributed evidence and moves
to rollback; it cannot masquerade as a completed phase.

## Release is a request, not a voltage claim

The policy never drives high. Its canonical inactive and cleanup intent is
`Release`.

| Evidence | Permitted conclusion |
|---|---|
| policy emitted `Release` | software requested line release |
| matching copied release receipt | producer reported applying release |
| E1 test-point voltage and timing | the exact physical line met its qualified idle window |

Initialization emits a correlated baseline `Release` and does not become
transaction-ready until `confirmCleanup()` accepts the matching copied
receipt. Reset does the same while preserving an initialized lifecycle.

Timeout, cancellation, producer failure, and contradictory phase evidence emit
one canonical release rollback intent. Until its matching receipt arrives, the
snapshot is `ReleaseUnconfirmed`; no new transaction can begin. Exhaustion is
the exception: when a unique cleanup correlation cannot be minted, the whole
triggering call rejects atomically instead of promising an unconfirmable
release.

Shutdown supersedes any earlier pending cleanup with a fresh closing lifecycle
and correlated `Release`; a receipt for the superseded intent is stale. The
policy remains initialized only so `confirmCleanup()` can accept the closing
receipt. After confirmation it becomes inert. A missing or failed receipt
never allows software to claim that a physical bus is idle or de-energized.

A successful operation is not consumable merely because its data slots
finished. `completedEvidence()` returns `ResourceBusy` while its terminal
`Release` remains unconfirmed, returns `Ok` with the complete attributed
snapshot only after confirmation, and otherwise returns `NotInitialized`.

![a graphite hourglass runs, then empties beside one open-hand release card,
which remains in a tray as the same unresolved cleanup obligation on later
calls](../downloads/assets/064-deadline-cleanup-pencil.png)

## Receipt-free deadline service

`advance(now, intent)` is the only receipt-free service path. At or before the
deadline it leaves the owed phase unchanged. Only the first supplied time
strictly after the deadline emits at most one correlated release intent and
records timeout/rollback state.

It never:

- synthesizes a receipt or sampled level;
- marks a phase successful;
- retries an operation;
- polls conversion status;
- bypasses reset or shutdown cleanup; or
- turns repeated calls into multiple cleanup intents.

At and before the overall transaction deadline, the owed phase remains
unchanged. The first `advance()` strictly after it emits the one correlated
timeout-release intent. Per-phase receipt windows retain their separately
configured inclusive earliest/latest rules; they are not inferred from the
overall deadline.

## Deterministic proof

Host fixtures cover:

- an ordinary literal ROM bit stream plus all-zero rejection and byte-exact
  transport of all-one, wrong-family, and bad-CRC nonzero ROMs;
- every reset, release, presence, write, read, complete-slot, recovery, and
  operation-deadline boundary immediately below, at, and above;
- no presence, early/late presence, stuck-low, both copied bit values, and
  least-significant-first byte assembly;
- every first, middle, and final slot failure with retained prefix evidence;
- complete `MatchRomReadConversionStatus` traces for both copied result bits
  and no implicit retry;
- single-drop enforcement and bounded Search ROM straight, collision, branch,
  completion, cancellation, and replay traces;
- owner, lifecycle, configuration, request, transaction, operation, phase,
  slot, source, sequence, and time receipt-correlation failures, plus request
  and conversion-continuation ROM-binding failures;
- byte-identical duplicate, changed duplicate, regression, rollover,
  exact-half-range ambiguity, and exhaustion;
- producer failure, cancellation, reset, timeout, and shutdown from every
  phase through unconfirmed and confirmed release;
- `advance()` below, at, and beyond the deadline without synthesized evidence;
- `confirmCleanup()` with early, late, foreign, changed, failed, matching, and
  duplicate release receipts;
- parasite-power and every invalid enum rejection before mutation; and
- two policy instances producing byte-identical witnesses from the same
  copied trace.

## Compile-only Mega replay

The canonical sketch uses fixed synthetic requests, supplied microsecond
times, copied receipts, and named volatile result cells:

| Stage | Predict | Observe | Interpret |
|---:|---|---|---|
| initialize and confirm | one baseline release is owed, then confirmed | initialization status, release, ownership, lifecycle, and provenance cells | copied confirmation makes the policy transaction-ready without acquiring hardware |
| reject parasite request | state remains ready and unchanged | `Unsupported`, supply-mode, generation, and prediction cells | closed E0 power policy rejects before mutation |
| begin presence transaction | first owed intent is reset-low | request, transaction, phase, line-intent, and timing cells | the typed request starts one copied reset/presence sequence |
| apply presence sequence | one matching receipt advances one step until terminal release | receipt-provenance, slot, phase, sample, quality, and prediction cells | copied timing and presence evidence advance deterministically |
| confirm terminal release | completed transaction becomes consumable | release requested/confirmed, completion, and provenance cells | successful data is not complete evidence before cleanup confirmation |
| begin and trigger timeout | exact deadline remains pending; the first later service call requests rollback | status, deadline, quality, and release cells | timeout invents no receipt and leaves one release owed |
| confirm rollback, then shutdown | rollback confirmation permits shutdown; closing confirmation makes the policy inert | lifecycle, initialized, release, status, and terminal prediction cells | each copied release closes only its correlated software obligation |

These memory cells are the non-Serial E0 observation path. Compilation is
packaging evidence only. Do not upload the E0 replay as a bus driver or connect
a probe.

## External-power evidence remains open at E1a and E1b

No wiring table or formal schematic is authorized at E0.

E1a requires an exact externally powered reference specimen and a qualified
external weak pull-up. Evidence must establish:

- manufacturer marking, package, pin order, primary datasheet, and incoming
  inspection;
- exact Mega endpoint and resource ownership with open-drain-safe behavior;
- pull-up value, loaded high/low rails, sink current, bus capacitance/length,
  rise time, and noise margin;
- measured reset, presence, write, read, sample, slot, and recovery timing at
  named physical test points under interrupt pressure;
- startup, reset, rollback, timeout, stuck-low, shutdown, and independent
  power-removal behavior; and
- a non-Serial line/activity observation path with separate
  resource-acquisition and safe-state records.

E1b is a separate parasite-power campaign. It requires an exact strong-pull-up
switch and power capability with handoff timing, current and rail margin,
exclusive conversion hold, contention prevention, rollback, stuck-on
handling, and independent power removal. Ordinary `Release` or output-high
drive can never substitute for this evidence.

No immersion, hot surface, flame, heater, medical or food measurement,
unattended thermal source, waterproof claim, or unknown three-pin module is
authorized. Listing `18B20 Temp` does not identify a physical specimen, and
Lesson 062's `Digital Temperature` remains a distinct unidentified family.
