# Lesson 069 — qualified motion recorder

Status: **Host verified E0 deterministic project; exact no-LTO resource review
complete, all powered acceptance remains open**

Energy class: **E0 copied records, supplied time, caller-owned volatile
storage, and inert presentation/export intent only**
Safety boundary: **no sensor, pin, bus, interrupt, clock, button, display,
LED, RTC, SD card, filesystem, or powered circuit**

`QualifiedMotionRecorder` composes the two preceding lessons into a bounded
motion-recording project:

`one qualified source + copied normalized records + copied controls + supplied time → bounded volatile trace + script progress + presentation intent`

The recorder never probes for a device, chooses between sources, reads a
clock, drives a display, or writes a file. At E0, “recorded” means copied into
a fixed caller-owned buffer for the current process lifetime. It does not
mean written, flushed, durable, or recoverable after power loss.

## What interchangeable means

One recorder session fixes one exact source identity and all relevant schema,
normalization, calibration, mapping, qualification, recorder, and script
revisions. Every accepted record must match that configuration.

Interchangeability means that separate, independently configured sessions can
use the same recorder contract. It does not mean hot swapping, automatic
detection, voting, blending, fallback, or accepting whichever source reports
first. A session configured for one copied fixture cannot silently continue
with another.

The `Mpu6050` and `Qmi8658` source tags remain provenance-shaped negative test
seams at E0. A matching enum value is not evidence that either physical
device, carrier, register map, voltage domain, range, scale, or mounting
orientation has been identified. Positive E0 replays use synthetic copied
fixtures only.

## One atomic qualification envelope

The recorder admits motion only when the Lesson 068 qualification witness is
bound to the exact Lesson 067 record being considered. The copied envelope
preserves, rather than merely summarizes:

- source identity and identity domain;
- schema, normalization, source-configuration, calibration, mapping, and
  qualification revisions;
- source observation time and sequence;
- qualification generation, attempt, state, reason, and status;
- window bounds and evidence digest; and
- normalized vectors, readiness, saturation, and producer status.

The digest helps detect correlation mistakes, but it is never a substitute
for comparing and retaining the authoritative fields. Pairing a newer record
with an older qualification decision, changing one revision, or reading two
mutable child snapshots independently rejects the update.

A malformed envelope changes nothing. The recorder, caller result, and every
trace byte remain unchanged. A structurally valid but unqualified envelope
may publish explicit fault presentation, but it cannot append a record or
advance the script.

## Lifecycle

The intended public lifecycle is:

| Mode | Meaning | Permitted progress |
|---|---|---|
| `Inert` | Constructed but not initialized | None |
| `AwaitingQualification` | Configuration is valid; no admitted witness | Accept one matching terminal qualification |
| `Ready` | One source is qualified for this configuration | Begin a nonzero session |
| `Recording` | The hand-motion script and bounded trace are active | Append at most one correlated record per update |
| `Complete` | The final script step has completed | Inspect or request export of the volatile trace |
| `Fault` | A visible source, chronology, correlation, or capacity fault dominates | Reset through the documented lifecycle |
| `Shutdown` | Presentation is inert and recording is disabled | Repeated shutdown is an idempotent no-op |

Construction is inert. Initialization validates configuration and supplied
capacity. Qualification admits one matching terminal Lesson 068 witness.
Beginning a session requires a new nonzero session identity. Reset starts a
new empty lifecycle generation; it does not retain qualification or trace
progress from the old session. Shutdown publishes canonical inert intent and
appends nothing.

The exact C++ declarations are frozen with the implementation. Their public
shape follows this responsibility:

```cpp
struct QualifiedMotionRecorder
{
    explicit QualifiedMotionRecorder (
        const MotionRecorderConfig& config) noexcept;

    Status initialize (TimePoint now, uint16_t recordCapacity) noexcept;

    Status qualify (
        TimePoint                            now,
        const InertialQualificationEvidence& evidence) noexcept;

    Status begin  (TimePoint now, uint32_t sessionId) noexcept;
    Status update (TimePoint                    now,
                   const InertialRecord&         record,
                   const MotionRecorderControl& control,
                   MotionRecordImage*           records,
                   uint16_t                     recordCapacity) noexcept;

    Status acknowledgeExport (TimePoint now) noexcept;
    Status reset             (TimePoint now) noexcept;
    Status shutdown          (TimePoint now) noexcept;
    Status result            (MotionRecorderResult& result) const noexcept;

    bool initialized () const noexcept;
};
```

The recorder is noncopyable and nonmovable. It owns no heap allocation,
hardware endpoint, hidden clock, callback, or retained child reference.
Caller-owned storage is bounded explicitly, and no pointer supplied for a
synchronous result is retained.

## The six-step hand-motion script

The deterministic script contains:

1. `Rest`
2. `TiltForward`
3. `TiltBack`
4. `TiltLeft`
5. `TiltRight`
6. `ReturnToRest`

An accepted record is attributed to the current step before that step may
advance. A step advances only on its explicit completion predicate and
minimum-duration evidence. An unqualified sample, source fault, stale record,
capacity failure, presentation event, or export request cannot advance it.
The last step remains terminal until reset.

The closed `MotionRecorderCommand` carries exactly one command per update.
`Reset` is handled before record and trace validation; a byte-identical command
envelope replay is idempotent. A changed duplicate, regression, future
observation, backward chronology, or exact modular half-range ambiguity
rejects atomically.

## Bounded trace without silent loss

The caller supplies fixed-capacity record cells. Accepted records append in
order until the declared capacity is full. The recorder never wraps, replaces
the oldest cell, coalesces samples, partially writes a cell, or pretends a
dropped sample was saved.

Each append is transactional:

1. validate lifecycle, source identity, revisions, correlation, chronology,
   controls, and capacity;
2. derive the qualification-frame observation and Lesson 044 orientation;
3. stage and validate one canonical record image;
4. write the complete destination cell; and
5. commit the count, recorder sequence, script progress, and result together.

Capacity exhaustion is a visible `CapacityExhausted` health state. The prior
trace remains intact, the count does not increase, and the fresh sample is not
misrepresented as recorded. Recorder-sequence exhaustion faults before
sequence zero. A byte-identical replay does not append twice.

## Canonical records are not C++ object dumps

Each project record uses a fixed normative image with explicit magic, version,
encoded length, byte order, reserved-zero bytes, and integrity check. It binds:

- recorder revision, session identity, record ordinal, and script step;
- complete source and Lesson 067 revision identity;
- qualification attempt, revision, mapping, and evidence correlation;
- source sequence and observation time;
- mapped acceleration, angular rate, readiness, saturation, and health;
- Lesson 044 orientation result; and
- the digest of the canonical Lesson 067 record.

Raw object layout, padding, compiler ABI, `memcmp`, and memory addresses never
define record identity. Encoding and decoding validate every closed enum,
reserved bit, semantic relationship, and integrity field before publishing.
Corruption or a short destination leaves both output and recorder state
unchanged.

## Fault-dominant presentation

Presentation is a semantic value, not a display driver. It names recorder
health, the current script prompt, trace count, full state, orientation
value-or-fault content, character-display tokens, and RGB color/blink tokens.

A source or qualification fault dominates a valid-looking angle. Stale,
not-ready, saturated, unqualified, or producer-fault evidence cannot leave a
cached healthy orientation visible as current. Trace-full and
storage-not-implemented indications remain distinct from sensor faults.
Display self-test intent cannot qualify a source, append a record, clear a
fault, or advance the script.

The existing Lesson 044 policy remains the only pitch-and-roll presentation
seam. Lesson 069 does not introduce a second orientation algorithm or
reinterpret source axes.

## Export is only a request

E0 export is a request-and-acknowledgement handshake over the caller-owned
record images. A request means that another layer may inspect the prepared
volatile trace. An acknowledgement closes that request in the policy model.

Neither event proves that bytes reached an SD card, filesystem, RTC-correlated
record, cache, or durable medium. A future storage adapter must separately
correlate prepare, write, flush, verification, interrupted-write recovery,
media removal, capacity, and power-loss evidence before the project may use
durability language.

## Predict, observe, interpret

Before replaying a fixture, predict the session mode, current script step,
record count, orientation-valid flag, health token, and whether the next
update is eligible to append.

Observe the named caller-owned result cells and trace cells after each update:
source health, script progress, orientation validity, trace count, capacity
state, RGB intent, character-display intent, and record outcome. These values
are the non-Serial observation path. Serial output may explain them but is not
the evidence.

Interpret an unchanged trace after rejection as proof of atomic policy
behavior, not physical sensor or storage behavior. Interpret a completed
synthetic script as deterministic composition evidence, not proof that a
board moved in the described direction or that a real inertial device is
interchangeable.

## Failure interpretation

| Observation | Meaning at E0 | Next check |
|---|---|---|
| `AwaitingQualification` persists | No exact matching terminal witness was admitted | Compare source and every configured revision |
| Source fault token with plausible angles in the input | Fault dominance suppressed untrusted orientation | Inspect producer status and bound qualification evidence |
| Correlation rejection | Record and witness do not describe the same observation | Compare source, sequence, time, attempt, revisions, and digest |
| Stale at one millisecond past the limit | The copied record exceeded the inclusive age bound | Check supplied `now` and original `observedAt` |
| Script step does not advance | The record was rejected, unqualified, too early, or lacked an eligible `Advance` command | Inspect status, health, duration, and copied control identity |
| `CapacityExhausted` | The declared caller buffer is full | Preserve the trace; reset with deliberate new storage |
| Export requested but no file appears | Correct E0 behavior: no media adapter exists | Do not infer a write, flush, or durable save |
| Shutdown presentation is inert | Recording and presentation intent are disabled | Do not interpret this as a physical power-removal action |

## No circuit at E0

There is no pin-by-pin wiring section because Lesson 069 has no circuit at E0.
Its resource budget is zero pins, zero timers, zero interrupts, zero buses,
zero endpoints, and zero powered devices. The Mega example is a compile-only
synthetic replay whose observable results are caller-owned values.

The reviewed implementation budgets are:

| Resource | Target | Hard review limit |
|---|---:|---:|
| Recorder object | 512 B | 768 B |
| One canonical project record | 128 B | 160 B |
| Conservative synchronous stack | 768 B | 1,024 B |
| Recurring composition SRAM | 2,048 B | 3,072 B |
| Residual Mega 2560 SRAM | at least 4,096 B | at least 3,072 B |
| Arc replay flash | 32 KiB | 40 KiB |

The canonical Mega replay runs the Lesson 067 normalizer, the genuine Lesson
068 qualifier, and the Lesson 069 recorder. It measures 39,428 bytes of flash
and 2,347 bytes of static SRAM. Exact no-LTO evidence measures 35,144 bytes of
flash, 2,347 bytes of static SRAM, 861 bytes of synchronous stack, a 509-byte
recorder object, a 128-byte canonical record image, and 4,856 bytes of residual
SRAM. Exact flash, static SRAM, and stack miss their targets by 2,376, 299, and
93 bytes respectively; independent fingerprint-bound review accepted all
three below their hard limits. Object, image, residual SRAM, and every hard
gate pass. Any measured source, configuration, layout, toolchain, probe,
fixture, or call-graph change makes the review stale.

## Open powered acceptance

Powered support remains split into independent acceptance cards:

- E1a: one exact MPU6050 or QMI8658 chip and carrier revision, including
  primary register map, identity, reset, address strap, voltage, pull-ups,
  range, scaling, byte order, data-ready behavior, mounting axes, calibration,
  timing, and rollback;
- E1b: exact character display, RGB LED, and copied-control button endpoints,
  including ownership, polarity, current limits, startup, self-test, fault
  dominance, rollback, and named electrical observation points; and
- E1c: exact RTC, SD/media, and filesystem behavior, including timestamp
  domain, write/flush verification, corruption recovery, capacity, removal,
  and power-loss behavior.

Evidence for one sensor family or carrier revision never closes another
family’s card. An I2C scan, marketing name, plausible identity byte, or copied
golden trace is insufficient. No unidentified revision is powered.

Until those cards close, Lesson 069 remains a deterministic, volatile recorder
policy over copied evidence. It makes no claim of physical acquisition,
orientation accuracy, display operation, clock accuracy, media persistence,
or safe powered behavior.
