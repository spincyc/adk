# Lesson 045 — stationary tabletop balance instrument

Status: **E0 synthetic replay; powered fixture and bench acceptance open**

Energy class: **E0 copied-evidence project**
Safety boundary: **stationary, lightweight, hand-tilted tabletop model; no actuator**

`BalanceInstrument` composes copied inertial, joystick, and button observations
into one atomic, replayable frame:

`copied frame → validate → orient → freeze/select → scale → presentation intent`

The result is a memory-only light, diagnostic, and tone-intent record. The
project owns no sensor, bus, pin, clock, LED, sounder, display, actuator,
storage device, callback, or heap allocation.

## One atomic frame

Each `BalanceInstrumentInput` supplies one coordinator time and sequence plus
three independently timestamped and sequenced observations. The instrument
validates the complete frame before changing any state. It rejects malformed
control records, future timestamps, sequence regression, and changed data at
an already accepted frame identity. A structurally valid frame with excessive
input skew is instead accepted as explicit evidence and atomically commits a
latched `Fault` safe state with `InvalidArgument`.

An exact complete-frame replay is idempotent. A producer record reused in a
later frame does not repeat its joystick or button event. The inertial sample
may be reused only with canonically recomputed age, readiness, quality, gap,
and status. This lets a current sample become visibly stale without inventing
a new sensor sample.

Rejected frames leave the output, policy histories, sequence baselines,
diagnostic epoch, and caller-owned replay storage unchanged. Structurally valid
fault and ineligible frames are instead accepted as explicit safe-state
evidence.

## Button-only freeze authority

A qualified button press is the sole action that freezes or unfreezes a
measurement. Tilt, joystick movement, elapsed time, and a repeated held button
cannot freeze it.

- Freeze captures the current frame's eligible `Level` or `Tilted` estimate,
  not the previous frame.
- Frozen evidence retains source, range, configuration and calibration
  revisions, timestamp, sequence, readiness, freshness, saturation, and
  status.
- New healthy frames continue updating `liveEvidence` while
  `frozenEvidence` remains stable.
- Sensitivity changes re-render the frozen angle but do not rewrite the
  measurement.
- Stale, saturated, unsteady, beyond-range, invalid, or failed evidence cannot
  become the frozen value.
- Shutdown clears frozen state and publishes the configured invalid, no-tone
  intent.

## Sensitivity

The copied joystick observation carries axes in `[-1000, 1000]` permille and
an already-qualified event. Positive-only axes mean `Increase`, negative-only
axes mean `Decrease`, zero axes mean `None`, and mixed signs mean
`Contradictory`.

Increase and decrease move by one configured step and clamp at the configured
minimum and maximum. A contradictory event is admitted as an unhealthy no-op.
Sensitivity starts at the midpoint rounded toward the minimum and is volatile:
shutdown and restart restore the configured starting behavior. No second
potentiometer authority is implied.

## Modes, recovery, and precedence

| Mode | Meaning |
|---|---|
| `AwaitingFrame` | initialized, but no complete frame has been accepted |
| `Live` | the newest eligible estimate drives presentation intent |
| `Frozen` | retained evidence drives presentation while live evidence continues |
| `Fault` | a producer or skew fault is latched; controls are ignored and tone is off |
| `Recovering` | a healthy fault acknowledgement was accepted; one later forward healthy frame is still required |

Each admitted frame follows fixed precedence:

1. reject uninitialized use, invalid configuration, or a malformed/future
   frame;
2. latch non-OK producer status in inertial, button, then joystick order;
3. latch excessive input skew;
4. preserve an existing fault latch;
5. make stale, saturated, unsteady, or beyond-range evidence visibly
   ineligible with tone off;
6. apply freeze or unfreeze;
7. apply sensitivity;
8. publish ordinary live intent.

`acknowledgeFault()` succeeds only after a newly accepted complete frame is
fully healthy. It enters `Recovering` without erasing live or frozen evidence,
sensitivity, the diagnostic epoch, or accepted-frame identity. An exact replay
cannot finish recovery. The first later forward healthy frame returns to
`Live` and suppresses controls carried by that recovery frame.

## Deterministic replay trace

The canonical compile-only sketch uses constant synthetic inertial fixtures
and copied joystick/button records. It copies complete RGB, mono-diagnostic,
tone, live/frozen evidence, mode, sensitivity, and producer-status results
into named memory cells.

| Replay stage | Predict | Observe in the host harness | Interpret |
|---|---|---|---|
| startup | `AwaitingFrame`, tone off | mode and complete awaiting intent | policies initialized without acquiring hardware |
| level and four tilts | `Live` with bounded direction intent | estimate, light intent, and provenance cells | stationary synthetic values passed validation |
| joystick steps | sensitivity changes within configured clamps | sensitivity and re-rendered intent | copied control event changed presentation gain |
| button press | `Frozen` from the current frame | retained frozen evidence beside changing live evidence | only explicit button authority froze the result |
| stale, saturated, or unsteady input | visibly ineligible, tone off | quality/status plus complete diagnostic intent | unsafe numeric evidence did not drive ordinary presentation |
| producer failure | latched `Fault` | fault intent and independent producer statuses | precedence remained visible without erasing attribution |
| acknowledge then forward healthy frame | `Recovering`, then `Live` | mode sequence with controls suppressed on recovery | recovery required fresh progress |
| shutdown | invalid no-tone intent | safe-state result cell | no physical command or stale current label remains |

Serial output is optional supporting evidence. The named result cells are the
non-Serial E0 observation path. Mega compilation is packaging evidence only:
do not execute this sketch on a powered Mega or use a powered debugger as E0
evidence.

## Resource boundary

The implementation uses fixed storage, bounded constant-time policy work, and
no dynamic allocation. `BalanceFrameStorage` is caller-owned and must remain
alive and unmodified for the instrument's initialized lifetime. The project
retains compact live and frozen evidence rather than duplicating either
six-axis payload.

The current AVR GCC 7.3 measurement records:

| Measured item | AVR bytes |
|---|---:|
| `BalanceInstrumentConfig` | 76 |
| `BalanceInstrumentInput` | 101 |
| caller-owned `BalanceFrameStorage` | 102 |
| `BalanceInstrumentOutput` | 119 |
| `InertialObservationPolicy` | 80 |
| `OrientationPolicy` | 38 |
| `BalancePresentationPolicy` | 95 |
| `BalanceInstrument` | 339 |
| resident four-policy composition plus replay storage | 521 |
| worst live composition with input and returned output | 741 |

The compiler-derived `update()` stack estimate is 399 bytes and the
compiler-derived coexistence figure is 1,140 bytes. A minimal linked core probe
measures 17,220 bytes of flash and 65 bytes of static SRAM.

The canonical Mega sketch measures 26,398 bytes of flash, below its 28,672-byte
ceiling, and 1,898 bytes of static SRAM, below its 2,048-byte ceiling. The
final no-LTO sketch has a reviewed 851-byte foreground stack bound. Adding
15 bytes for Arduino timer-zero ISR preemption gives a conservative 866-byte
bound and leaves 5,428 bytes after static storage, 4,404 bytes beyond the
1,024-byte gate. That is compiler/link evidence, not a measured runtime
canary; runtime high-water evidence remains an E1 acceptance item.

The design-stress disposition revised the project-object target and hard
threshold to 352 and 384 bytes respectively, so the measured 339-byte
`BalanceInstrument` passes both. A successful compile alone does not establish
physical behavior or runtime stack use. The E0 path claims zero digital pins,
ADC inputs, timers, interrupts, I2C transactions, and physical endpoint
current.

## Stationary tabletop and powered-work boundary

The intended future fixture is a small, lightweight, inert platform resting
fully on a table and tilted gently by hand. It carries no loose load and has
no sharp edge, pinch point, motor, stabilization loop, launcher, vehicle, or
stored-energy path. It is not for walking, wearable use, load balancing,
navigation, attitude-and-heading reference, fall detection, or any
safety-relevant decision.

There is no E0 wiring table, pin assignment, I2C address, register transaction,
or formal electrical schematic. MPU-6050 and QMI8658 variants require separate
future adapters. Each adapter remains blocked on exact delivered-specimen
identity, primary electrical and register sources, rail and logic-level
qualification, mounting evidence, and independent bench acceptance.

Physical joystick, button, RGB/diagnostic LEDs, sounder, resistors, timing,
current, acquisition, observation, shutdown, and power-removal evidence also
remain open E1 work. Host replay, compilation, documentation, and memory
measurements are not physical acceptance.
