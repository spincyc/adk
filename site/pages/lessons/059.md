# Lesson 059 — attributable MAX7219 presentation

Status: **E0 deterministic register-intent policy; exact powered MAX7219
fixture and bench acceptance open**

Energy class: **E0 copied frame, command, and receipt values only**
Safety boundary: **no SPI bus, chip-select pin, matrix, module, supply, or
powered circuit**

`Max7219PresentationPolicy` turns one committed 8-by-8 logical frame into a
bounded sequence of correlated MAX7219 register intents:

`copied frame + fixed orientation → one command → one exact copied receipt`

The policy never calls transport code. Its E0 evidence consists of copied
command values, recording-seam receipts, and named memory result cells.
Acceptance by that seam does not prove that a MAX7219 received a command, a
matrix changed, chip select moved electrically, or shutdown made a powered
fixture dark.

## Logical frame and orientation

The independent logical frame has eight rows. Row zero is the top, and bit
seven is the leftmost pixel before transformation. The fixed orientation is
one of `Identity`, `Rotate90`, `Rotate180`, or `Rotate270`; transformation
occurs only after the complete logical frame is known.

Intensity is validated in the MAX7219 domain from 0 through 15. The canonical
E0 replay fixes it at 1. Initialization retains the desired display as
logically dark while it emits this exact register sequence:

1. shutdown;
2. display test off;
3. decode mode off;
4. scan limit seven;
5. bounded intensity;
6. rows one through eight; and
7. normal operation.

Every intent is an exact 16-bit, MSB-first register write represented as one
register-address byte and one data byte. Display-test mode is never used as
the learner self-test.

## Preview, preflight, and commit

Frame publication follows `preview()`, `canCommit()`, and `commit()`. A
candidate carries the policy owner token, lifecycle generation,
configuration revision, and base presentation generation. Foreign, stale,
altered, or consumed candidates reject without changing the desired frame.

A successful commit updates copied desired state but issues no transport
command. Under Lesson 060's exclusive ownership, both child policies are
preflighted before either pure commit, so the pair cannot fail halfway because
of an ordinary stale preview.

The policy is inert after construction, non-copyable, and non-movable. It
retains no caller pointer, reads no clock, allocates no heap storage, invokes
no callback, retries nothing, sleeps nowhere, and does bounded work on every
call.

## One command, then one receipt

One `service()` opportunity may publish at most one copied command. It carries
all correlation needed to reject unrelated evidence:

- owner token and lifecycle generation;
- configuration revision and presentation generation;
- operation index; and
- one register-address byte and one data byte.

The caller executes that value through the recording seam and later supplies
one copied receipt with the same correlation fields, accepted-byte count,
chip-select cleanup evidence, observation time, and complete `Status`.
`acceptedByteCount` is limited to 0, 1, or 2.

Success requires all three facts: `Status::Ok`, two accepted bytes, and chip
select recorded inactive afterward. A non-OK result may report zero or one
accepted byte. Non-OK with two accepted bytes, or OK with a short count, is
contradictory evidence and faults without advancing the submitted
generation.

A call without the exact outstanding receipt changes nothing. Foreign, stale,
regressing, exact-half-range, or changed duplicate receipts reject
atomically. An identical duplicate is idempotent.

## Partial writes are evidence, not success

MAX7219 is write-only in this boundary, and a multi-row update is not
physically atomic. An accepted prefix cannot be rolled back. The snapshot
therefore distinguishes:

- desired frame;
- last fully submitted frame;
- partial accepted prefix;
- blank requested;
- shutdown command accepted; and
- physically indeterminate state.

The first failed operation, register, row, and status remain primary fault
provenance. Failure enters cleanup-pending and schedules one best-effort
shutdown command for a later service opportunity. Cleanup status is retained
separately and never overwrites the first failure.

The submitted presentation generation advances only after all eight row
receipts have been accepted. Progress is caller-paced rather than
time-driven, and restart repeats complete configuration before ordinary frame
submission.

## Compile-only replay

The canonical Mega 2560 sketch uses named volatile result cells as its
non-Serial observation path:

| Stage | Predict | Observe | Interpret |
|---:|---|---|---|
| initialize | logical dark state and first configuration command | lifecycle, operation, register, and data cells | policy initialized; no bus or endpoint acquired |
| configure | one exact command is outstanding at a time | command and correlated receipt cells | the recording seam accepted copied bytes in order |
| orientation | one logical marker moves to the transformed location | logical and transformed row cells | orientation is explicit and deterministic |
| frame commit | desired state changes before submitted state | desired and submitted generation cells | commit issued no hidden transport work |
| row failure | prefix and first failure remain attributable | row, byte count, status, and cleanup-pending cells | a partial write was not promoted as a frame |
| cleanup | one later shutdown command is attempted | primary-fault and cleanup-result cells | best-effort cleanup did not erase provenance |
| shutdown | later service emits no ordinary row command | shutdown and lifecycle cells | logical activity stopped; physical blanking remains unproved |

Predict each complete copied value before the call, inspect the result cells,
and compare them with the deterministic host trace. Those observations prove
E0 packaging and policy behavior only; compilation does not prove that a Mega
executed the sketch.

## Deterministic proof

Host tests cover the exact configuration order and bytes, all 64 logical
pixels, all four orientations, every row byte, frame-candidate ownership and
generation collisions, one-command service pacing, exact receipt
correlation, identical duplicates, changed duplicates, stale and foreign
receipts, modular ordering, and exact-half-range rejection.

Failure cases cover byte zero and byte one of every configuration and row
write, partial-prefix attribution, contradictory accepted-byte evidence,
chip-select cleanup failure, best-effort shutdown, restart, lifecycle
exhaustion, shutdown, and byte-identical replay. Recording-seam tests prove
byte position and chip-select framing; policy tests prove only the copied
receipt contract.

The exact no-LTO AVR resource gate records linked flash, static SRAM, policy
object size, conservative synchronous stack, residual SRAM, public value
sizes and traits, and toolchain fingerprints. The Lesson 059 targets are 16
KiB flash, 1,024 bytes static SRAM, 384 bytes synchronous stack, and a
192-byte policy object; the corresponding hard ceilings are 20 KiB, 1,536
bytes, 512 bytes, and 256 bytes. Final measured values must pass the gate
before promotion. These are compiler results, never runtime stack-watermark,
electrical, transport, optical, or physical evidence.

## E1b remains open

At E0, resource-acquisition evidence is “no resources requested.” Safe-state
evidence is the copied logical-dark state, blank request, and accepted
recording-seam shutdown receipt. Those are separate policy observations, and
neither proves that a powered matrix is dark.

E1b may begin only after the exact MAX7219 IC or module revision and its
schematic are recorded. Qualification must establish:

- the matrix anode/column and cathode/row mapping and its fixed orientation;
- RSET value, segment-current calculation, and local decoupling;
- 4.0–5.5 V supply compatibility and Mega logic-level compatibility;
- serial timing, chip-select framing, and reuse of the existing `SpiDevice`;
- startup, injected failure, shutdown, and observed blanking;
- worst-case simultaneous current and loaded supply behavior; and
- transactional resource acquisition with separate safe-state evidence.

An unknown or low-value module current-setting resistor may exceed this
project's 100 mA USB campaign. Keep that module unpowered until its exact
network is qualified. The existing `SpiBus` terminal-fault recovery ambiguity
must also be resolved before promotion; a MAX7219-specific retry path must not
hide a shared-bus lifecycle defect.
