# Lesson 055 — constraint and clue model

Status: **E0 deterministic clue-policy integration; exact passive inputs,
presentation hardware, and bench acceptance open**

Energy class: **E0 copied-evidence policy**
Safety boundary: **fixed categorical clue values and memory result cells
only; no endpoint, display, storage medium, latch, lock, or power path**

`ClueConstraintModel` evaluates a fixed puzzle-specific directed acyclic graph
over copied clue observations:

`expected clue sources + fixed rules + explicit time + copied observations → stable rule and model dispositions`

The model has exactly 12 clue slots and 12 rule slots. A rule can compare at
most four clues and depend on at most four earlier rule results. It is not a
generic solver, identity system, access decision, security boundary, or
physical-room controller. A `Solved` disposition means only that a fictional
puzzle rule set is satisfied in memory.

## The evidence wall replay

The canonical compile-only Mega sketch treats the model as an evidence wall
whose result cells can be inspected without Serial.

1. **Acquire:** `setup()` first constructs a deliberately cyclic four-rule
   fixture and proves that initialization rejects it.
2. **Configure:** the sketch replaces that fixture with a valid four-rule
   diamond and assigns every clue its exact expected source identity.
3. **Start:** it initializes an inert model with a 100-microsecond inclusive
   freshness limit.
4. **Observe:** `loop()` copies clue cards into their identity-matched array
   slots and supplies an explicit observation mask and `now`.
5. **Decide:** `update()` validates the complete envelope, admits it
   atomically, and evaluates the fixed DAG once in topological order.
6. **Actuate:** the sketch writes only named `EvidenceWallResultCell` memory
   values. It owns no physical output.

The replay grows from a four-rule teaching graph to the full twelve-rule
capacity:

| Stage | Predict |
|---:|---|
| 1 | one admitted clue satisfies rule 0 while its three dependent rules remain blocked |
| 2 | four matching clues satisfy the complete diamond |
| 3 | twelve matching clues satisfy the maximum chained fixture |
| 4 | evidence one tick beyond the inclusive age limit produces `StaleEvidence` |
| 5 | one explicitly contradictory clue produces `ContradictoryEvidence` and blocks its dependents |

Each result cell retains the generation, selected clue provenance, observation
time, satisfied and blocked masks, model disposition, first and final rule
dispositions, operation status, and prediction result. Predict those values,
inspect the named cells, and interpret them as deterministic software
evidence. They do not prove that a sensor, display, Arduino, latch, or room
was observed.

## Fixed identities and atomic updates

Configuration is copied at construction and becomes immutable after
initialization. `clueCount` and `ruleCount` are each in `1..12`, with dense
zero-based IDs. Each configured clue has one exact expected source identity:
a nonzero source ID, configuration revision, and session epoch.

Array position is identity, not insertion order. For clue `i`:

- observation-mask bit `i` selects array slot `i`;
- the selected observation must contain clue ID `i`; and
- an unselected slot must be canonical zero.

All unused sources, rules, terms, prerequisites, observations, and mask bits
must also be canonical zero. The model rejects duplicate terms or
prerequisites, invalid categories, out-of-range IDs, self-dependencies, and
cycles before it accepts evidence. Cycle validation and rule evaluation are
iterative and bounded; there is no recursion, heap allocation, callback,
retry loop, or hidden clock.

An update validates every selected and unselected slot before changing live
state. If any field is malformed, future-dated, ambiguously ordered, from the
wrong source, or contradictory to retained same-sequence evidence, the whole
envelope rejects. Evidence cells, rules, masks, generation, and retained
status remain unchanged. A successful update admits the selected observations
as one generation and reevaluates all rules at the supplied `now`.

An identical observation at the same source sequence is idempotent evidence:
it does not replace the retained payload. The accepted update still advances
the model generation and reevaluates freshness at its new `now`. A changed
payload at the same sequence is a source contradiction. Forward sequence
ordering, wrap, regression, and the exact half-range ambiguity follow the
repository unsigned modular ordering rule.

## Freshness and deterministic precedence

`maximumEvidenceAge` is in the unsigned modular half range and may be zero.
Freshness uses the inclusive interval from `observedAt` through
`observedAt + maximumEvidenceAge`: evidence is fresh exactly at the limit and
stale one tick later. Zero therefore means same-time evidence only. Future,
regressing, and exact-half-range-ambiguous time relationships reject atomically
instead of being reinterpreted as stale. Ordinary unsigned modular rollover
remains valid.

Prerequisite failure is considered before a rule's terms. Among terms, the
published precedence is:

1. invalid, source-fault, or timing-fault evidence;
2. stale evidence;
3. contradictory evidence;
4. missing evidence; and
5. an ordinary category mismatch.

The highest-precedence blocking class wins; within that class, the first
blocker in definition order is reported for diagnosis. The complete satisfied
and blocked masks remain deterministic. A zero-term rule is satisfied when
all its prerequisites are satisfied, including vacuous satisfaction when it
has none. `UINT8_MAX` means “no blocker”; zero remains a valid term or
prerequisite index.

`evidence(clueId)` and `rule(ruleId)` return stable copied records. An invalid
ID returns `StatusCode::InvalidArgument` with a fieldwise canonical-zero value
and does not mutate the model. `reset()` clears evaluation while keeping the
model initialized; `shutdown()` and destruction return it to an inert state.
The model is non-copyable, non-movable, and owns all of its live rule and
evidence state.

## Deterministic proof and resource evidence

Host tests enumerate all 4,096 directed-edge masks over four labeled rules and
accept exactly the acyclic graphs. They also enumerate all 4,096 observation
masks and cover slot identity, canonical padding, maximum capacities,
zero-term rules, dependency joins, every evidence quality, blocker
precedence, freshness boundaries, sequence and time rollover, exact
duplicates, same-sequence collisions, rejection atomicity, lifecycle
transitions, invalid result IDs, and fieldwise replay.

The canonical Mega build measures **8,886 bytes of flash** and **1,261 bytes
of static SRAM**. `ClueConstraintModel` measures **636 bytes on AVR**. The
reviewed synchronous stack estimate is **412 bytes**.

The preferred object target was 512 bytes and the preferred stack target was
384 bytes, so both preferred targets are missed. The measured values remain
inside their reviewed hard ceilings of 640 bytes and 512 bytes respectively.
The accepted target misses preserve the owner-owned, lossless twelve-clue and
twelve-rule state rather than moving lifetime-sensitive storage to the caller
or discarding provenance. Any later growth beyond a hard ceiling blocks
promotion and requires a new design decision.

These figures are compiler, linker, AVR layout, and conservative static-call
analysis evidence. The stack figure is not a measured runtime high-water
mark. None establishes powered behavior or physical acceptance.

## What remains physically open

E0 claims zero pins, ADC channels, timers, interrupts, buses, resource
registry entries, endpoints, displays, supplies, or actuator paths. Its
resource-acquisition observation is therefore “no resources requested.” Its
safe-state observation is the copied snapshot and named evidence-wall memory
cells; Serial is optional and unnecessary.

E1 remains open until exact passive clue inputs and low-voltage,
current-limited presentation hardware have separately documented identities,
electrical limits, authoritative formal schematics, resource ownership,
rollback, safe-state observations, and signed bench records. Servo, relay,
latch, lock, and other powered actuation must remain physically absent at E1.

Any future E2 demonstration requires a separately qualified restrained servo
or inert current-limited low-voltage relay-and-lamp load plus independent
physical load-power removal. It may never attach to a door, gate, lock,
occupied enclosure, alarm, emergency lighting, egress route, or life-safety
system. Software `Solved`, reset, shutdown, and stop states are not safety
functions.
