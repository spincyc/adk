# Lesson 018: Inert access-control trainer

Status: host-verified project package; physical acceptance open.
Energy class: E1 in this lesson. No motor or external load supply is connected.

This project composes the matrix keypad, deterministic `AccessTrainer`, RGB
state, a character display, and a separate soft-latch indicator. It teaches
entry, submission, denial, timed lockout, fault handling, and replay. It is not
a lock, authentication system, alarm, or security recommendation.

The narrative loop is:

`observeOperator → decideAccess → presentAccess`

`AccessTrainer` owns no hardware or hidden clock. Digits append to a bounded
teaching entry, `Star` clears, and `Hash` submits. The engine publishes
`SoftLatchIntent` and `softLatchOpen`, but this E1 circuit translates that intent
only to a resistor-limited LED on D30. Servo pulses, load power, motion, door
hardware, relays, solenoids, and real credentials are absent.

## Circuit and evidence

| Role | Mega pins | Required observation |
|---|---|---|
| 4×3 keypad rows | D22–D25 | TP-R0 at D22 exposes one scan row |
| keypad columns | D26–D28 | key events appear in the state presentation |
| common-cathode RGB | D5, D6, D7 through separate resistors | blue/white/green/amber/red state |
| soft-latch intent LED | D30 through at least 220 Ω | on means “open requested,” never “open proven” |
| acquisition witness | built-in D13 | on only after all owners initialize |
| 16×2 display | D34–D39 plus module-rated contrast/backlight wiring | prompt and count; never entered digits |

RGB meanings are blue `Ready`, white `Entering`, green `Granted`, steady amber
`Denied`, a slow 500 ms on/500 ms off amber pulse for `LockedOut`, and red
`Fault`. Color is redundant with the display and latch-intent LED; it is never
the only evidence.

Predict the state, display prompt, RGB pattern, and D30 level before each trace.
Observe TP-R0, the indicators, and display together. Interpret each signal
narrowly: D13 supports acquisition, D30 supports software intent, and neither
proves physical position or security.

## Required deterministic traces

- correct four-key fixture, submit, exact grant deadline, automatic close;
- wrong entry, clear, retry, and success;
- three denials, lockout one tick before/at/after its deadline;
- invalid chord, stuck key, keypad fault, and clock rollback;
- display or presentation failure producing fault and closed intent;
- reset and shutdown from every state;
- two identical traces producing identical snapshots and audit intents.

Audit records contain event kind, sequence, and event time, never entered
digits. The example consumes each event into a fixed one-record LCD sink:
`A#### KIND` remains visible for one second, then row two returns to entry
count. It retains no hidden history or credential data. Serial logging is
optional supporting evidence.

## CLI workflow

```sh
make host-test-access-trainer
make arduino-Lesson018AccessTrainer
make upload EXAMPLE=Lesson018AccessTrainer PORT=/dev/ttyACM0
make monitor PORT=/dev/ttyACM0 BAUD=115200
make hardware-card LESSON=018
make lessons
make site
```

The hardware card remains open until a person records the exact board, parts,
voltages, resistor values, TP-R0/D30 observations, reset behavior, and safe
shutdown evidence.

## Motion is a later, separate gate

Lesson 017's `BoundedServo` and `ServoOutput` describe bounded command intent
and explicit D44/Timer5 ownership. They are not enabled here. A later E2
variant requires an identified servo, independent current-limited supply,
physical load-power disconnect, restrained paper-pointer fixture, measured
current and waveform evidence, and completed Lesson 017 bench acceptance.
Software shutdown is never the physical stop method.
