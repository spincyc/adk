# Lesson 049 — local identity records

Status: **E0 synthetic-record integration; powered adapters, durable media,
and bench acceptance open**

Energy class: **E0 pure policy**
Safety boundary: **copied fixture evidence and caller-owned memory only**

`LocalIdentityRegistry` validates copied UID-shaped observations and maps them
to bounded local paper-bin records:

`copied identifier + explicit time + fixed record image → local bin result`

An identifier is a lesson-local token. It is not a credential, proof of
possession, person identity, authentication result, authorization system, or
security boundary. Checksums detect malformed fixed images; they do not
provide integrity against an attacker.

The registry owns no RFID reader, keypad, pin, endpoint, timer, interrupt,
bus, storage transport, supply, or moving hardware. It does not read a card,
write nonvolatile media, dispense a part, or authorize motion.

## Fixed limits and public records

An identity contains 4–10 significant bytes in a fixed ten-byte field. Bytes
after the declared length must be zero. All-zero and all-`0xff` values are
reserved fixture sentinels and are rejected.

The public limits are:

| Limit | Value |
|---|---:|
| identity bytes | 10 |
| local bindings | 8 |
| carousel bins | 8 |
| canonical image slots | exactly 2 |
| bytes per image | 160 |

`IdentityEvidence` retains its synthetic source identity, occurrence time,
sequence, copied identifier, and complete producer status.
`IdentityBinding` associates one identifier with a local bin, nonzero
revision, and checksum. `IdentityRegistrySnapshot` exposes the current
disposition, selected bin, binding and failure counts, pending transaction
state, committed image generation, matched binding revision, accepted
sequence, and status.

The dispositions distinguish known, unknown, duplicate, lockout, full
directory, missing enrollment authority, pending enrollment, malformed
evidence, corrupt or unsupported images, indeterminate commit, and storage
fault. A known result alone exposes the matched nonzero binding revision.

## Lifecycle and borrowed storage

Construction is inert. The registry borrows:

- a bounded live binding array;
- two complete 160-byte canonical image slots; and
- one 160-byte candidate-image buffer.

Those arrays must outlive the registry and must not move. Initialization
validates the complete configuration, a nonzero registry configuration ID, a
nonzero caller-supplied `instanceEpoch`, buffer extents, non-overlap, both
image slots, and every binding before copying a selected image into the live
table. A zero epoch is rejected. Failed initialization leaves the object and
borrowed arrays unchanged.

The epoch names one object lifetime. A caller reconstructing a registry—even
at the same memory address and over the same supplied image bytes—must provide
a distinct nonzero epoch. It is not persisted in the canonical image and is
never derived from an address, hidden counter, or process state.

`reset()` clears observation, lockout, authorization, and ordinary candidate
state while retaining committed bindings, image generation, and source replay
identity. `shutdown()` publishes an inactive lifecycle and is idempotent. An
unresolved external commit is preserved for reconciliation instead of being
silently discarded.

## Canonical two-slot image

Each 160-byte image has fixed magic `0x4944`, schema version `1`, encoded
length, nonzero registry configuration ID, generation, bounded binding count,
eight canonical entry locations, zero reserved bytes, and a final
CRC-16/CCITT-FALSE checksum.

Multibyte integers are unsigned little-endian. Unused entries are all zero.
Each used entry stores the significant length, ten-byte zero-padded identity,
bin, nonzero binding revision, and its own checksum. Unknown flags or schema,
wrong lengths or configuration, noncanonical padding, malformed entries, and
checksum failures are rejected.

Recovery validates both supplied slots before selection:

- one valid slot dominates a corrupt, torn, erased, unsupported, or
  foreign-configuration slot;
- two valid unequal generations use modular half-range ordering;
- equal generations must be byte-identical;
- ambiguous generation separation fails closed; and
- two invalid slots never become an empty directory.

These rules prove deterministic reconstruction from caller-supplied bytes.
They do not claim nonvolatile retention, atomic writes, wear endurance, or
power-loss survival.

## Observation and lockout

`observe(now, evidence)` accepts only the configured synthetic source domain,
well-formed status, canonical identifier, admissible occurrence time, and
forward sequence history. Same-domain sequence deltas `1..INT32_MAX` advance;
the half-range is ambiguous and larger deltas regress. Exact replay may age
but cannot create a new attempt. Changed payload at an accepted sequence is
malformed.

Unknown evidence increments a saturating failure count once per new sequence.
Reaching the configured maximum begins a bounded lockout. The exact expiry
boundary is usable. A known identifier clears failures only after lockout
expires. Structural, source, timing, and image faults take precedence and do
not increment the count.

## Transactional enrollment

Ordinary observation cannot enroll an identifier. Enrollment is an explicit
external transaction:

1. `previewEnrollment()` validates a fresh unknown identifier, bin, capacity,
   lockout, and current committed generation without mutating the live table.
2. `previewExport()` returns a bounded view of the complete canonical
   candidate image in the caller-owned scratch buffer.
3. An external coordinator may write the inactive durable slot, synchronize
   it, read it back, and validate it.
4. `acknowledgeExternalCommit()` accepts matching durable evidence and
   atomically installs exactly the reconciled candidate.

The candidate `owner` is exactly the registry's caller-supplied
`instanceEpoch`. The candidate also binds the base and candidate generations,
operation ID, scratch index, and checksum. Supplying a distinct epoch for each
reconstructed lifetime prevents a candidate copied from an earlier object
from passing owner checks after same-address reconstruction. Foreign, stale,
changed, negative, or indeterminate acknowledgements preserve the prior table
and retryable candidate while requiring reconciliation. A byte-identical
repeat of an already accepted acknowledgement is idempotent; other duplicate
or changed metadata is rejected without mutation.

This API models the handoff to future storage. E0 performs no physical write.

## Deterministic replay

The compile-only Mega sketch uses a const synthetic trace, an eight-binding
RAM array, two fixed image slots, one candidate buffer, and named result
cells. Its narrative remains:

`setup(): acquire fixture storage → configure registry → start replay`

`loop(): observe one copied identifier → decide scripted enrollment action → record result`

The replay covers known and unknown identifiers, duplicate and occupied-bin
enrollment, lockout boundaries, cancellation, corrupt-image restart, external
acknowledgement, and recovery. Host tests additionally cover every byte and
length boundary, checksums, capacity, chronology and rollover, changed replay,
foreign and stale candidates, torn images, reset, restart, and fieldwise
determinism.

Named memory cells are the non-Serial observation path at E0. Initialization
status separately proves only that configuration and borrowed memory were
accepted. Neither the result cells nor the all-inactive state prove electrical
resource acquisition, safe voltage, physical storage, or powered shutdown.

## Resource and powered-work gates

The E0 policy is fixed-storage and allocation-free. It owns exactly zero pins,
ADC channels, timers, interrupts, buses, resource-registry entries, endpoints,
supplies, storage transports, or moving hardware.

The public registry object measures **121 bytes** against its **112-byte
target** and **128-byte hard ceiling**. The canonical Mega sketch measures
**7,026 bytes flash** and **1,113 bytes static SRAM**, inside its respective
**16,384-byte** and **1,280-byte** ceilings. Its conservative stack/ISR gate
reserves at least **512 bytes** and leaves more than the required **768 bytes**
after globals and that allowance. Compilation and size results are packaging
evidence only.

E1 remains open for exact RFID and keypad specimens, a qualified nonvolatile
adapter, primary electrical evidence, pin and resource maps, powered
observation paths, rollback, safe-state and power-removal evidence, an
authoritative formal schematic, media measurements, and bench acceptance.
E2 motion and gate hardware remain outside this component and are introduced
only through separately qualified later work.
