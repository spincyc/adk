# Temperature and humidity

Status: **host verified; hardware acceptance open**<br>
Energy class: **E1** — USB-powered Mega, low-voltage sensor, and
resistor-limited status LED

This lesson separates the condition of a sensor transaction from the meaning
of its decoded values:

`scheduled request → electrical exchange → validated sample → health pattern`

`ClimateSensor` publishes fixed-point temperature, relative humidity, an
observation time, and an explicit state. No response, checksum failure,
out-of-range data, and a stale formerly valid sample remain different
outcomes. A consumer must inspect the state before treating either numeric
field as a measurement.

## Learning outcomes

After the lesson, you should be able to:

- schedule acquisition without blocking the run loop;
- distinguish transport failure from an invalid decoded measurement;
- use supplied time to decide whether a valid sample has become stale;
- replay the same timestamped frames and obtain the same results; and
- verify software health and electrical activity through separate signals.

## Reference circuit

The reference build uses an Arduino Mega 2560, a supported
DHT11-compatible 5 V sensor module, and one resistor-limited RGB status LED.
The exact module identity, required data pull-up, timing limits, LED resistor
values, and current calculation must be taken from the selected parts'
primary documentation before bench acceptance.

Planned bill of materials:

- Arduino Mega 2560 and USB cable;
- one identified DHT11-compatible 5 V module;
- one common-cathode RGB LED;
- one current-limiting resistor per LED channel;
- a data pull-up only when required by the selected module;
- breadboard and jumpers; and
- a logic analyzer or oscilloscope for the data test point.

The signal wiring reserves D22 for sensor data and names the sensor data
connection `TP13`. Sensor VCC connects only to the documented supported
supply, and sensor ground joins Mega GND. D5, D6, and D7 drive the red, green,
and blue channels through separate 330 Ω resistors.

Do not infer a pull-up value or module pin order from this page: similarly
named sensor boards differ. Inspect the circuit with USB power removed. Stop
on an unidentified module, uncertain polarity or rating, a warm part, repeated
board reset, or a signal outside the board supply rails.

## Predict, observe, interpret

Before each update, predict both the sample state and the expected evidence.
Observe `TP13` for the electrical request and response, then observe the RGB
health pattern:

| Planned indication | Meaning |
|---|---|
| Slow blue pulse | Resource acquired; no completed frame yet |
| Steady green | Current sample is valid and fresh |
| Two red pulses | Transport timed out |
| Three red pulses | Checksum or decoded-value validation failed |
| Amber | Last valid sample exceeded the selected freshness limit |

The LED reports the software state; it does not prove that temperature or
humidity is physically accurate. `TP13` can prove that an exchange occurred;
it does not prove that the frame decoded correctly. Resource acquisition is
checked separately from shutdown: after `shutdown()`, the eventual bench card
must verify that D22 returns to high impedance.

## Evidence and open work

Deterministic host tests exercise validation bounds, transport and checksum
faults, staleness, lifecycle behavior, timestamp boundaries, waveform decoding,
and identical replay. The canonical Mega sketch compiles, and the printable
lesson records the exact wiring and diagnosis workflow. Physical acceptance
remains open, so this lesson makes no measured claim about voltage, current,
sensor accuracy, startup, or shutdown behavior.
