# Lesson 065 — qualified four-probe 18B20 set

Status: **E0 deterministic copied-evidence component; exact probes, powered
single-wire adapter, thermal accuracy, and bench acceptance open**

Energy class: **E0 copied transaction evidence and volatile policy state only**
Safety boundary: **no sensor, GPIO pin, bus, pull-up, strong pull-up, supply
rail, clock, display, recorder, persistent medium, heated object, immersion, or
powered fixture**

`Qualified18B20ProbeSetPolicy` turns complete copied Lesson 064 transaction
snapshots into four stable, attributed temperature slots:

`configured ROMs + copied search passes + copied conversion evidence + copied scratchpads + supplied time → four qualified observations`

It does not discover or operate a physical bus. It cannot reset a line, select
a device, start a conversion, supply conversion power, read a scratchpad, or
identify an unknown package. Its output is policy evidence, not a claim that
four physical thermometers are present or accurate.

## Exactly four configured identities

Construction fixes four complete ROM codes in configured order. Each ROM must
use family byte `0x28`, have a valid Dallas CRC-8 in byte seven, and differ
from the other three ROMs. There is no runtime count, wildcard, zero-filled
optional slot, insertion, or replacement.

Each slot also fixes:

| Configuration | Meaning |
|---|---|
| resolution | exactly 9, 10, 11, or 12 bits |
| conversion deadline | exactly 94, 188, 375, or 750 ms for 9-, 10-, 11-, or 12-bit resolution |
| maximum age | freshness limit in the supplied millisecond time domain |
| lower and upper raw bounds | allowed signed temperature interval in sixteenths Celsius |
| maximum step | greatest accepted change between consecutive trusted conversions |

Discovery order never becomes identity. A ROM found first, last, or in a
different permutation always maps back to its configured slot. A valid but
unknown ROM is bounded fault evidence; it never displaces one of the four
configured roles. A repeated ROM is `DuplicateIdentity`, not a second probe.

Dallas CRC-8 starts at zero, processes least-significant bits first with the
reflected polynomial `0x8c`, and has no final XOR. The policy checks the ROM
CRC and the nine-byte scratchpad CRC independently.

## Lifecycle and staged cycles

The caller lifetime-reuses one private `Ds18b20CycleBuilder`. The builder is
noncopyable and nonmovable, owns fixed storage, and exposes no mutable fields.
Construction stores configuration and prepares inert unqualified storage
without validating or accepting evidence. `initialize()` validates the four
configured roles and creates four unqualified slots; repeated initialization
is idempotent. `reset()` retains configuration and initialized state while
clearing the accepted snapshot and replay history. `snapshot()` copies the
current four-slot result, and `initialized()` reports lifecycle state.

One call stages one complete transaction at a time:

```cpp
explicit Qualified18B20ProbeSetPolicy (
    const QualifiedDs18b20SetConfig& config) noexcept;

Status initialize () noexcept;
void reset () noexcept;

Status beginCycle (
    TimePoint now,
    uint8_t sourceId,
    uint16_t configurationRevision,
    uint32_t cycleSequence,
    TimePoint observedAt,
    Ds18b20CycleBuilder& builder) const noexcept;

Status ingestSearchPass (
    Ds18b20CycleBuilder& builder,
    const OneWireTransactionSnapshot& transaction,
    const OneWireSearchState& requestSearch) const noexcept;

Status finishSearch (
    Ds18b20CycleBuilder& builder,
    bool searchComplete,
    bool searchOverCapacity,
    Status producerStatus) const noexcept;

Status ingestConversionStart (
    Ds18b20CycleBuilder& builder,
    uint32_t conversionGeneration,
    const OneWireTransactionSnapshot& transaction) const noexcept;

Status ingestConversionStatus (
    Ds18b20CycleBuilder& builder,
    uint32_t conversionGeneration,
    const OneWireTransactionSnapshot& transaction) const noexcept;

Status ingestScratchpad (
    Ds18b20CycleBuilder& builder,
    uint32_t conversionGeneration,
    TimePoint scratchpadObservedAt,
    const OneWireTransactionSnapshot& transaction) const noexcept;

Status finalizeCycle (
    TimePoint now,
    const Ds18b20CycleBuilder& builder,
    QualifiedDs18b20Snapshot& snapshot) noexcept;

Status snapshot (QualifiedDs18b20Snapshot& snapshot) const noexcept;
bool initialized () const noexcept;
```

`finishSearch()` records whether enumeration ended normally, retained a
producer failure, or proved that a fifth result exceeded the fixed evidence
capacity. During an active cycle, only `finalizeCycle()` can commit the staged
cycle to the policy snapshot and replay history. The `const` staging methods
mutate only the caller-owned builder; `initialize()` and `reset()` perform
their documented lifecycle mutations outside that staged commit.

A failed begin, ingestion, or search-finish operation leaves every builder
byte unchanged. Failed finalization leaves both policy state and caller output
unchanged. A byte-identical complete replay is idempotent; a changed duplicate
with the same cycle identity rejects rather than being guessed equivalent.
Construction is inert, and the policy is noncopyable, nonmovable, heap-free,
callback-free, and clock-free.

## Search evidence is a chain

The builder retains at most four completed `SearchRomPass` witnesses. The
first request must contain the empty search state. Every later request must
match the preceding completed result field-for-field, and no pass may follow
a result whose `lastDevice` flag is already set.

A complete nonempty enumeration ends with `lastDevice == true`. One through
four returned devices can therefore prove configured identities missing. Four
results ending with `lastDevice == false` can instead prove over-capacity, but
cannot prove that the configured set is complete. Contradictory flags, broken
search-state continuity, malformed transactions, or invalid correlation are
structural errors and reject atomically. A structurally valid zero-pass,
truncated, producer-failed, unterminated, or over-capacity search instead
commits typed `TransportFault` evidence; absence is never inferred from it.

Each complete Lesson 064 snapshot is validated transiently, including its
operation, addressed ROM, external-power mode, accepted-slot count, presence,
confirmed release, request status, transaction quality, and terminal status.
The normalized transaction reference retains only request sequence,
transaction generation, start time, and completion time. The builder retains
the common Lesson 064 owner, lifecycle, and configuration tuple once for the
complete cycle rather than repeating it in every compact reference.

This distinction is deliberate: malformed structure, contradictory flags,
broken search continuity, invalid enums, and crossed identity or correlation
return `InvalidArgument` or `CapacityExceeded` without committing anything.
A well-formed cycle that carries producer failure, an incomplete search, an
over-capacity marker, or an invalid discovered ROM instead commits a
four-slot snapshot whose set quality is `TransportFault`. A duplicate
discovered ROM commits `DuplicateIdentity`; a valid foreign ROM commits
`UnknownIdentity`; and only a terminal successful search can commit
`Missing`.

## Conversion and scratchpad qualification

Conversion start, one copied conversion-status observation, and scratchpad
read must correlate to the exact ROM and one nonzero conversion generation.
The witness retains a complete compact reference for conversion start, an
optional complete compact conversion-status reference, and a complete compact
scratchpad-read reference. If status is present, it must immediately follow
conversion start and the scratchpad read must immediately follow status. If
status is absent, the scratchpad read must immediately follow conversion
start. Crossed ROMs, lifecycles, request or transaction sequences,
generations, configurations, or non-forward transaction times reject before
mutation.

The scratchpad must be exactly nine bytes with a valid CRC. Its resolution
bits must name a supported resolution and match the configured slot. Raw
temperature is decoded as signed sixteenths Celsius; resolution-dependent
undefined low bits are masked before the policy publishes an interval.
Consequently, `rawSixteenths` is accompanied by
`lowerRawSixteenths` and `upperRawSixteenths` instead of being presented as
false precision.

`+85 °C` is not automatically an error. Without a matching completed
conversion it is `ResetDefaultWithoutConversion`; after fully correlated
completion it can be a valid reading. A low conversion-status bit strictly
before the configured deadline is `ConversionPending` and retains the
previous trusted value and original observation time. Pending at the exact
deadline or later is `TransportFault`. Completed-high evidence is accepted at
the exact deadline and becomes `TransportFault` only after it.

A plausible-range or step check uses widened signed arithmetic. A change
exactly at the configured maximum is accepted; a larger change is
`ImplausibleStep`. This warning retains the new settled, CRC-valid,
conversion-correlated value and makes it the next comparison baseline, so one
real step cannot permanently lock the slot. Corrupt, pending, missing, or
transport-fault evidence does not refresh that baseline.

## Stable output and fault visibility

`QualifiedDs18b20Snapshot` always contains four slots in configured order.
Each slot retains its complete ROM, cycle and conversion attribution, read
transaction generation, original observation time, inclusive `freshThrough`
time, signed raw value and resolution interval, expected resolution, age,
quality, and status.

Probe quality is one of:

- `Unqualified`
- `ConversionPending`
- `Current`
- `ScratchpadCrcFault`
- `ResolutionMismatch`
- `ResetDefaultWithoutConversion`
- `ImplausibleStep`
- `Stale`
- `Missing`
- `DuplicateIdentity`
- `TransportFault`

The set additionally reports `validCount`, `presentMask`, `faultMask`, and a
set quality of `Unqualified`, `Complete`, `TransportFault`,
`DuplicateIdentity`, `UnknownIdentity`, or `Missing`. A deterministic
configured-slot precedence chooses the aggregate status without erasing any
slot's own outcome. A bad probe cannot vote itself into a cold, hot, or
healthy reading.

Freshness begins at the supplied scratchpad observation time. Evidence older
than its configured maximum becomes `Stale`; future, backward, or exact
half-range-ambiguous time rejects structurally. A missing slot retains its
configured identity and last trusted reading with increasing age. A later
valid reappearance returns to the same slot. A CRC-valid, completed-conversion
reading publishes `freshThrough = observedAt + maximumAge`; the endpoint
itself is still fresh, and the next millisecond is stale. Lesson 066 consumes
this inclusive modular-time seam so it can reassess a copied slot at its own
supplied presentation time without borrowing Lesson 065 configuration or
silently extending freshness.

Lesson 064 transaction timestamps are microseconds; Lesson 065 cycle,
scratchpad-observation, finalization, and age timestamps are milliseconds.
The caller asserts the mapping between those independent clocks. The policy
binds both in the normalized witness and validates forward chronology within
each domain, but never invents a shared epoch or derives one clock from the
other. Cycle sequences are nonzero and modularly forward:
`UINT32_MAX` followed by `1` is valid, while zero, regression, and an exact
half-range ambiguity reject.

## Predict, observe, interpret

The canonical Mega replay uses copied transaction snapshots and synthetic
scratchpads only. Before each replay, predict the four qualities, configured
slot order, masks, and valid count. Observe the named volatile result cells
with a debugger, logic-independent memory inspection, or the optional Serial
summary. Then interpret:

| Replay | Expected policy evidence |
|---|---|
| four complete correlated reads | four `Current` slots in configured order |
| permuted search results | unchanged configured slot order |
| one bad scratchpad CRC | one `ScratchpadCrcFault`; other slots remain attributable |
| conversion still low before deadline | `ConversionPending` with prior trusted value retained |
| complete search omits a configured ROM | that stable slot becomes `Missing` |
| CRC-valid reappearance | the same slot becomes current again |
| excessive signed step | `ImplausibleStep`, not an accepted extreme |
| valid incomplete or fifth-device search | committed set `TransportFault`; absence is not inferred |

Named volatile cells are the E0 non-Serial observation path. They prove only
that the deterministic replay produced the expected memory values. They do
not prove GPIO activity, a powered bus, conversion timing, probe presence, or
thermal accuracy.

## Resource boundary

The terminal Mega 2560 publisher probe measured:

| Boundary | Measured | Target | Hard limit |
|---|---:|---:|---:|
| ordinary replay flash | 13,662 B | 12,288 B | 16,384 B |
| ordinary replay static SRAM | 1,438 B | 1,024 B | 1,536 B |
| isolated no-LTO flash | 16,196 B | 12,288 B | 16,384 B |
| isolated no-LTO static SRAM | 1,438 B | 1,024 B | 1,536 B |
| conservative synchronous stack | 533 B | 448 B | 640 B |
| policy object | 764 B | 512 B | 768 B |
| caller-owned builder | 477 B | 448 B | 512 B |
| caller-owned snapshot/result | 180 B | 256 B | 512 B |
| recurring policy plus builder | 1,241 B | 960 B | 1,280 B |
| recurring plus lifetime-reused phase value | 1,421 B | 1,216 B | 1,792 B |
| residual SRAM after static, stack, and 128 B reserve | 6,093 B | 3,072 B | 2,048 B floor |

The ordinary and exact flash, static SRAM, stack, policy-object, builder,
recurring-storage, and lifetime-peak target misses were accepted after
independent review. Every hard gate passes. In particular, the four-byte
policy-object margin is a zero-growth constraint: any ABI change requires a
fresh fingerprint, measurement, and review. The design retains an exact prior
normalized cycle for collision-free changed-duplicate rejection, while the
caller lifetime-reuses one builder and one phase value instead of keeping
duplicate globals.

The terminal evidence fingerprint is
`350ddd1f6cefef2f5da249f295632339119c0f42d669a0a3a4732c36fed177cb`;
an independent rereview reproduced the tuple and returned clean.
Lesson 066 must separately measure the recurring composition in which Lesson
064, this policy, its reusable builder, and the mapper remain live together.
These are compiler/linker and storage measurements, not evidence of a powered
probe, electrical timing, conversion behavior, or thermal accuracy.

At E0 the hardware-resource claim is exactly zero pins, timers, interrupts,
buses, registry entries, sensors, pull-ups, and power resources.

## What remains open

E1 work requires an exact specimen and complete shared fixture, including:

- manufacturer and package identity, complete ROM behavior, cable and
  encapsulation construction, and incoming inspection;
- pin order, local external supply, ordinary pull-up, bus length and
  capacitance, rails, current, rise time, and reset/presence/slot margins;
- resolution-specific conversion timing, repeated four-device operation,
  disappearance, reconnect, and injected faults;
- a separately qualified non-Serial conversion/activity and selected-probe
  observation path; and
- an authoritative schematic, pin/resource map, power budget, uncertainty,
  safe-state evidence, and recorded bench acceptance.

Parasite power and strong pull-up remain a separate E1b campaign. `Release`
never means powered conversion support. This lesson authorizes no immersion,
hot surface, heater, flame, medical or food use, preservation claim,
unattended thermal source, waterproof-probe claim, or unknown three-pin
module. The authorized inventory label `18B20 Temp` is not specimen identity.
Lesson 062's unidentified `Digital Temperature` family cannot satisfy this
gate.
