# Lesson 036 — magnetic passage logger

Status: **host verified; physical acceptance open**

Energy class: **E0 core and persistence fixtures; provisional E1 indicators**
Safety boundary: **inert records and presentation only; no actuation**

The logger commits accepted passage evidence before presenting a count:

`accepted passage → frozen clock and label → durable commit → presented count`

`MagneticPassageLogger` consumes only accepted Lesson 035 records. It borrows an
abstract `Rtc`, one `PassageLedger`, and a narrow `PassageCountDisplay`
implemented here by a `SevenSegmentPassageCountDisplay` adapter. It does not
resample sensors, decode an encoder, implement a filesystem, move a gate,
identify a person, or actuate a load.

The RTC, byte-addressed storage, and passage sources used here are deterministic
host fixtures. Physical RTC, removable media, magnetic specimens, persistence,
and exact-revision wiring remain open.

## Frozen durable entry

`LoggedPassage` retains:

- accepted sequence and resulting committed count;
- acceptance time and direction;
- local `None/A/B/C` label;
- copied position evidence;
- the complete `ClockReading`; and
- explicit sequence-gap evidence.

Labels are metadata, not identity, authentication, access authority, or a
safety decision. A degraded clock reading remains degraded.

## Lifecycle and snapshot

Initialization validates configuration, initializes ledger then RTC then
display, recovers the checkpoint, and rolls back in reverse order. Shutdown is
idempotent.

The snapshot exposes selected label, committed count and sequence, displayed
count, pending and bounded-overrun inputs, immutable frozen entry, recovery
disposition, accepted and committed pulses, persistent fault, presentation
status, and logger status.

Accepted and committed pulses last for the snapshot immediately after their
event. When clock, ledger, and presentation all succeed in one update, both
pulses are true in that same snapshot. To see the stages separately, inject a
deterministic RTC or ledger failure: D30 appears without D31, then retry the
same sequence and observe D31 only after durable commit. Persistent fault
remains until successful shutdown and reinitialization.

## Processing order

For a new accepted sequence:

1. freeze the record and current label;
2. read the abstract RTC;
3. build the resulting committed entry;
4. commit it against the expected checkpoint;
5. advance logical committed state only after ledger success; and
6. update the display only after durability.

A failed RTC read leaves the input pending and performs no ledger or display
operation. Retrying the same sequence reads the clock again. After the first
successful clock read, the frozen entry is immutable and ledger retries are
byte-identical.

A failed commit changes no committed count, sequence, generation, or display.
A newer passage while pending becomes one bounded `overrunInput`; it is not a
queue and is not silently committed.

Display failure cannot mutate durable state or cause a ledger retry.

## Sequence rules

Only `Accepted` records are consumable. An older sequence is rejected. An equal
sequence is an idempotent no-op only when direction, acceptance time, and
position match recovered durable evidence; disagreement is an invariant fault.

A forward sequence gap may commit, but the durable entry records
`sequenceGap=true`. Saturating counters and sequence limits never wrap
silently.

## Two-slot ledger

Each fixed-size slot stores magic, version, length, modular generation, the
explicitly encoded entry, resulting count and sequence, IEEE CRC-32, and a
valid marker. Integer widths and little-endian order are fixed; no C++ object
memory image is serialized.

Commit writes the inactive slot with erased marker, writes body and checksum,
synchronizes, writes valid marker `0xa5` last, then synchronizes again.

Recovery distinguishes:

| Evidence | Result |
|---|---|
| two erased slots | `Empty`, synthetic checkpoint `{0,0,0}` |
| valid plus erased/torn/corrupt/unsupported peer | recover valid entry and preserve peer disposition |
| two invalid non-erased slots | `BothInvalid`; stop |
| equal generation and identical bytes | `DuplicateIdentical`; recover slot zero |
| equal generation and unequal bytes | `DuplicateGeneration`; stop |
| exact half-range generation separation | `AmbiguousGeneration`; stop |

If synchronization fails, the ledger rereads both slots. It claims committed
after reconciliation only when the new checkpoint is provably newest.

## Visible progression

The provisional indicator fixture uses:

| Path | Meaning |
|---|---|
| D30 LED through 1 kΩ | accepted input frozen |
| D31 LED through 1 kΩ | durable checkpoint advanced |
| D32 LED through 1 kΩ | persistent fault |
| D22/D23/D24 | 74HC595 count presentation |
| D28 | cycles label, previews `-/A/b/C` for one second, then restores count |

The display shows `committedCount % 10`; decimal point means ten or more.
Known indicator/segment current is bounded to 55 mA, excluding the Mega
baseline, shift-register package current, sensors, and pulls. These provisional
roles are not a physical storage or sensor schematic.

## Predict, observe, interpret

1. Recover two erased host slots; predict Empty and displayed zero.
2. Submit one accepted record with every fixture healthy; predict D30 and D31
   together in the successful update snapshot.
3. Fail an RTC read; predict D30 without D31, no ledger write, and no display
   change.
4. Retry the same sequence; predict one fresh clock read, frozen entry, and D31
   only after durable commit.
5. Fail a ledger byte or sync; inspect reconciliation before claiming commit.
6. Present a newer record while pending; inspect bounded overrun evidence.
7. Corrupt the inactive peer and restart; recover the valid entry with explicit
   peer disposition.
8. In host tests, fail presentation; verify committed state is unchanged and
   fault remains latched. The canonical Mega sketch does not inject display
   failure; it visibly exercises the RTC failure and retry path.

The Mega fixture deliberately fails its first abstract RTC read. D30 and D32
appear without D31, the same-sequence retry commits, and the persistent fault
remains visible for a bounded two seconds before shutdown/reinitialization
recovers the retained software slots. A D28 pull-up button cycles
`None/A/B/C`; because the edge is applied after the current logger update, a
simultaneous press changes only the next new sequence's label. The display
briefly previews `-/A/b/C`, then restores the durable count and decimal point.
The sketch preserves the current D30/D31 pulse intents across the cycle call,
checks its status, and refreshes the post-cycle snapshot; the preview is never
count authority.

Remove USB for heat, odor, reset, unstable rail, unexpected display or LED
state, or current-limit trip. Reconfigure only while unpowered. Do not connect
unknown sensors, physical RTC/media, motion, gates, locks, vehicles, launchers,
ignition paths, or safety systems.

## Software evidence and sources

Host evidence covers recovery dispositions, every byte and synchronization
failure, byte-identical retries, torn restart, generation and sequence edges,
pending overrun, lifecycle rollback, presentation faults, and deterministic
state bytes. These are not physical persistence, RTC, sensor, or bench claims.
