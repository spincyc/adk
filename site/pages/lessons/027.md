# Multi-source telemetry console

Status: **host verification in progress; physical acceptance open**
Energy class: **E1** — USB-powered Mega, passive buttons, display, and
resistor-limited evidence only

Lesson 027 is the project at the end of the receive-only telemetry arc. It
combines normalized samples, packet integrity, sequence tracking, freshness,
operator input, presentation, bounded attention, and stable records:

`source evidence → normalized reading → console decision → visible state → record`

The canonical example uses `TelemetryConsole`, `TelemetryRecordEncoder`, and
`TelemetryConsoleProject` directly. It adds only small Arduino adapters for
buttons, RGB presentation, and fixed record acceptance.

## Learning outcome

The learner builds a deterministic console for three owned compiled-in lab
fixtures. Input order cannot change configured source order. Missing sources
are explicit, and a bad presentation or failed record cannot rewrite source
health. Room labels are organizational examples, not a claim that this sketch
receives telemetry across rooms.

This is an educational annunciator. It is not a fire, burglar, medical,
industrial, environmental-safety, or emergency system. It makes no dispatch
decision and contacts nobody.

## Evidence model

The project keeps four words distinct:

- **capture** is timestamped physical evidence;
- **frame** is a bounded candidate protocol unit;
- **packet** is an ADK-owned telemetry envelope;
- **record** is the stable representation accepted by storage.

The console consumes a complete source set sorted by configured slot. A source
includes identity, kind, quality, sequence state, freshness, value, and decimal
exponent. The console produces health, attention intent, selected source,
record intent, and a complete status value.

| Health | Narrow meaning | Circuit evidence |
|---|---|---|
| starting | configured sources have not all reported | blue cadence |
| healthy | every expected source is valid and fresh | green cadence |
| degraded | an aging source or sequence gap exists | amber cadence |
| fault | stale, invalid, corrupt, duplicate, or missing evidence | fast red cadence |
| stopped | lifecycle is inactive | unlit |

Cadence distinguishes states without relying on color. Acknowledgement changes
the current signal from `Attention` to `Notice`; it never changes source
health, clears the red indication, or erases evidence. A new fault
reannounces. A bounded sounder is an optional extension, not starter wiring.

## Released E1 starter circuit

The canonical sketch uses:

- a `Next` pull-up button on D30, wired to GND;
- an `Acknowledge` pull-up button on D31, wired to GND;
- an RGB LED on D5--D7, with one 330 ohm resistor per channel;
- the built-in D13 LED, toggled after complete record acceptance;
- three compiled-in, owned fixture observations.

![Pencil orientation plate showing the Mega, display, next and acknowledge buttons, RGB health evidence, record LED, and their separate evidence paths](../downloads/assets/027-telemetry-console-pencil.svg)

The drawing includes optional display and sound extensions. The pin list above
and the sketch are authoritative for the starter circuit. There is no live
receiver, RF transmitter, unknown-radio capture requirement, actuator, relay,
external supply, or mains circuit.

## Narrative example plan

Objects appear in dependency order: runtime, button operator, RGB presentation,
bounded record sink, console, and project coordinator.

The run loop will read:

```cpp
observeTelemetrySources (now);
decideConsoleState      (now);
presentConsoleState     (now);
recordConsoleEvidence   (now);
```

The fixture presents source 101 temperature, source 202 relative humidity, and
source 303 contact state. Its fixed millisecond boundaries advance through
starting, one-by-one recovery, healthy, aging/degraded, stale/fault, and
recovery. Button events exercise selection and acknowledgement. The host suite
supplies byte-identical replay and failure injection.

## Presentation and logging are independent

The starter presentation maps health to RGB color and cadence. The project
still passes the selected source to the presentation interface, so an optional
display can show value, quality, and sequence without entering the decision.
A presentation failure is not a source fault.

A canonical bounded record is written on accepted sample, health transition,
operator acknowledgement, or periodic heartbeat. Simultaneous reasons collapse
to one record under a fixed priority. A failed write remains visible and uses
only a bounded retry policy; no queue grows in SRAM. Storage failure never
turns stale evidence healthy.

## Predict, observe, interpret

1. Predict the startup cadence before applying USB power.
2. Observe the display, RGB cadence, and source sequence as fixtures recover
   one by one.
3. Inject one aging source, then a stale source. Predict amber before red.
4. Acknowledge the cue. Observe silence while red health evidence remains.
5. Observe D13 toggle only after a complete record is accepted.
6. Invoke shutdown and measure the evidence pins separately from looking at
   the LEDs. Resource release and inactive electrical state are different
   claims.

Serial may show the same canonical record bytes, but it is optional supporting
evidence and never the only proof.

## Deterministic acceptance plan

Host coverage must include capacity limits, arrival-order independence,
duplicate and missing identities, complete health precedence, selection edges
and wrap, acknowledgement and reannouncement, time wrap, record trigger
priority, exact golden bytes, bounded failure retry, restart, and shutdown from
every health state. Two mixed-fixture replays must be byte-identical.

Physical acceptance remains blank until a person records the exact Mega board,
parts, supply, instruments, predictions, observations, shutdown measurements,
and deviations.
