\section*{The one specimen decision}

The normal kit path is an \textbf{identified, labeled DHT11 module}. The Elegoo
listing authorizes that family; it does not identify the board revision,
pin order, supply limit, current, or pull-up. Before power, read the markings
on the module in your hand and its matching documentation. Continue only when
they establish 5 V operation, \(+\), DATA (often S), \(-\), peak current, and
whether a DATA pull-up is already fitted. The drawing uses those \emph{names},
not an asserted left-to-right module order.

\safetybox{With USB unplugged, map the module's printed \(+\), S/DATA, and
\(-\) labels to breadboard columns 8, 9, and 10; rearrange the three module
leads if its physical order differs. Use one 330\,\(\Omega\) resistor for each
LED die. If identity, supply rating, current, LED common cathode, or pull-up is
uncertain, set that part aside. Stop for heat, odor, resets, or a warm jumper.}

If the identified module has pull-up \(R_P\), its worst DATA-low current is
\(5/R_P\); if it has none, fit the documented value from DATA to 5 V. The
330\,\(\Omega\) LED resistors keep ordinary documented indicator dies below
10 mA each when their minimum forward voltage is at least 1.8 V. Confirm the
module's peak current and keep module plus three LED channels below 35 mA.

The pictured module body is deliberately generic. Rotate or jumper the
identified module so its \emph{named} leads reach E8 \(+\), E9 DATA, and E10
\(-\); do not copy an unverified physical order. Likewise, preserve the
identified LED's electrical lead names if its leg order is not R--C--G--B.

Inspect every endpoint, plug in USB, and upload. The complete first powered
stage already has its payoff: blue pulses during the short start, then a steady
valid color appears. There is no Serial ritual or worksheet.

\section{Play with the air}

Cup your hands loosely around the sensor without touching it, then breathe
gently across the vents from several inches away. The steady valid color moves
from green (below 55\% RH), through cyan (55--69.9\% RH), to amber
(\(\geq70\%\) RH). Move it back into room air and watch it return. Lesson 014
will reveal the numbers.

Now unplug USB, lift only the D22-to-DATA jumper, and restore USB. The sketch
cannot fake success: two red pulses repeat because no bounded sensor reply
arrives. Unplug USB, restore that one jumper, and power again. Blue then green
is the recovery animation.

\section{What the code is doing}

The sketch reads in the same order as the build:

\begin{lstlisting}[style=adkcpp]
const adk::Status        status      = observeClimate     (now);
const adk::ClimateSample observation = decideClimateState (now);

if ((!status.ok () &&
     observation.state == adk::ClimateSampleState::Unavailable) ||
    !showClimateState (observation, now))
{
    haltClimateCircuit ();
}
\end{lstlisting}

\texttt{Dht11Sensor} owns D22. It drives DATA low only for the request and then
releases it to input; every edge wait has a deadline. It accepts a frame only
after all five bytes arrive, their checksum matches, and the decoded values are
in range. \texttt{sample(now, freshFor)} can later mark an old good frame stale
without touching the wire. Shutdown releases D22 and turns the RGB LED off.

The repository quietly replays good frames, timeouts, malformed pulses,
checksum faults, timing rollover, initialization failures, restart, and
shutdown. Those automated checks protect the lesson; they are not chores for
the learner.

\section{Next unlock}

You now have a circuit that distinguishes ``a sensor said something'' from
``a complete, current frame passed every rule.'' Keep this exact build intact.
