\section{Why input comes this early}

An output lets firmware report what it thinks. An input lets a person change what
firmware does. Together they form the smallest useful debugging panel. This lesson
keeps the two ideas separate: the new component reports the \emph{electrical} pin
level without debouncing or inventing button events. Lesson 003 will build those
policies on top.

\subsection*{Learning targets}

By the end, you can:

\begin{itemize}
    \item wire a normally-open switch from a Mega input to ground;
    \item explain why an internal pull-up gives an unpressed pin a known level;
    \item distinguish a sampled electrical level from an application's meaning;
    \item diagnose open, stuck-low, and noisy input evidence;
    \item drive the same input sequence through a deterministic host fake;
    \item explain how ownership and RAII leave the pin passive at shutdown.
\end{itemize}

\section{Safety and equipment}

\textbf{Energy class E1:} one USB-powered Arduino Mega 2560, one dry-contact
switch, the board's built-in LED, DMM, and an identified 10\,k\(\Omega\)
D13 weak-bias resistor. No external supply or stored-energy load is admitted.

\warningbox{Disconnect USB, barrel power, batteries, programmers, and powered
modules before changing wiring. The switch must connect D22 to GND---never to an
output. Do not connect 5\,V directly to GND. Use only a dry-contact switch in this
lesson. Do not use mains-powered, automotive, pyrotechnic, or unknown equipment.}

\textbf{Required:} Arduino Mega 2560 Rev3 or identified compatible board, USB
data cable, breadboard, normally-open momentary pushbutton, jumper wires, one
measured 10\,k\(\Omega\) resistor, the board's built-in LED, and a DMM with
documented input resistance and range.

Before wiring, identify the board revision, switch contact pair, USB source,
and cable. Confirm that
\texttt{LED\_BUILTIN} names the on-board diagnostic LED for the selected Mega
target. A visually similar four-leg switch is not identified until its open and
closed contact pair has been measured with all power removed.

\textbf{Before power:}
\checkbox\ switch straddles the breadboard center gap;
\checkbox\ one selected switch terminal reaches D22;
\checkbox\ its opposite terminal reaches Mega GND;
\checkbox\ there is no 5\,V jumper;
\checkbox\ continuity is open when released and closed when pressed.

\section{Predict the electrical behavior}

The Mega's internal pull-up is a weak resistor from the input to the board supply.
It establishes HIGH when the switch is open. Pressing the switch provides a much
lower-resistance path to ground, so the pin reads LOW. No external resistor is
required for this exercise.

\midrule

\evidencebox{\textbf{Vocabulary boundary.} DigitalInput reports
\texttt{Level::High} or \texttt{Level::Low}. \emph{Pressed}, \emph{released},
\emph{pressed edge}, and \emph{debounced} belong to a Button component.
The application may compare a level with LOW, but DigitalInput does not attach
human meaning to it.}

\section{Read state deliberately}

The canonical \texttt{Lesson002DigitalInput.ino} composes the input with Lesson
001's output:

\begin{lstlisting}[style=adkcpp]
constexpr adk::PinId ButtonPin = 22;

adk::Runtime      runtime;
adk::DigitalInput buttonInput (runtime.resources (), ButtonPin, adk::Pull::Up);
adk::MonoLed      led         (runtime.resources (), LED_BUILTIN);

void setup ()
{
    buttonInput.initialize ();
    led.initialize         ();
}

void loop ()
{
    buttonInput.update ();

    const bool pressed = buttonInput.read () == adk::Level::Low;
    led.set (pressed);
}
\end{lstlisting}

The variable is named \texttt{button} because of its circuit role; its type remains
DigitalInput. \texttt{update()} samples hardware and stores the level.
\texttt{read()} returns that stored level without a surprise hardware access.
\texttt{sample()} performs an immediate hardware read without changing the stored
level. Prefer \texttt{update()} plus \texttt{read()} for coherent application
frames; reserve \texttt{sample()} for deliberate diagnostics.

The compact example omits error reporting to expose the central composition. In
an application, compare every initialization result explicitly:

\begin{lstlisting}[style=adkcpp]
const adk::Status buttonStatus = button.initialize ();
const adk::Status ledStatus    = led.initialize    ();

if (!buttonStatus.ok () || !ledStatus.ok ())
{
    button.shutdown ();
    led.shutdown    ();
    return;
}
\end{lstlisting}

\textbf{RAII contract:} construction stores configuration without touching
hardware; successful \texttt{initialize()} claims and configures D22; repeated
\texttt{shutdown()} is harmless; destruction releases the claim and restores a
passive input state. Internal code reports failure with \texttt{Status}, not
exceptions, while cleanup remains correct if surrounding application code throws.

The downloadable canonical sketch begins with a 250\,ms acquisition pulse and
750\,ms dark separator before input behavior begins. It adds one controlled
acceptance action: hold
the switch continuously for three seconds to call \texttt{shutdown()} on the
LED and input. The sketch then remains passive until reset. This is a diagnostic
path, not button debouncing and not emergency power removal.

\section{Predict, observe, interpret}

The canonical sketch does not produce Serial output. Its primary evidence is
the built-in LED, driven from the same cached sample used by the application.
TP-IN is Mega D22 measured relative to GND; TP-LED is the built-in LED
indication. Repeat three voltage/LED trials for each state; the DMM observes
TP-IN voltage, while the LED exposes the cached firmware interpretation.

\section{Contact bounce is evidence, not yet a bug}

A mechanical contact may alternate HIGH--LOW several times while closing. At a
100\,ms reporting interval you may miss this; at a faster diagnostic interval you
may see it. DigitalInput must preserve raw evidence. It must not silently delay,
filter, or synthesize events.

\section{Deterministic host test}

The API and lifecycle below are \textbf{host-verified}. The physical circuit
remains \textbf{experimental} until you complete and record the Mega acceptance
checks. Host tests prove component rules without USB, wall-clock delays, or
nondeterministic contact timing.

\begin{lstlisting}[style=adkcpp]
fake::reset ();
adk::ResourceRegistry resources;
fake::setDigitalInput   (22, HIGH);
adk::DigitalInput input (resources, 22, adk::Pull::Up);

require (input.initialize ().ok ());
require (input.read () == adk::Level::High);

fake::setDigitalInput (22, LOW);
require               (input.sample () == adk::Level::Low);
require               (input.read () == adk::Level::High);

input.update ();
require       (input.read () == adk::Level::Low);

input.shutdown ();
input.shutdown ();
\end{lstlisting}

This mirrors the repository's fake-Arduino tests: \texttt{sample()} observes LOW
without mutating the cached HIGH; \texttt{update()} then stores LOW. Separate
tests verify the exact \texttt{pinMode}, \texttt{digitalRead}, claim-conflict,
invalid-pin, repeated-initialization, repeated-shutdown, and destructor traces.
A conflict is reported as a status:

\begin{lstlisting}[style=adkcpp]
adk::DigitalInput owner   (resources, 22, adk::Pull::Up);
adk::DigitalInput blocked (resources, 22, adk::Pull::Up);

require (owner.initialize ().ok ());
require (blocked.initialize ().error () == adk::StatusCode::ResourceBusy);
\end{lstlisting}

Preserve these assertions when extending the tests:

\begin{enumerate}
    \item construction alone produces no hardware call;
    \item initialization claims D22, selects \texttt{INPUT\_PULLUP}, and samples;
    \item repeated successful initialization produces no hardware call;
    \item \texttt{sample()} reads hardware without changing \texttt{read()};
    \item \texttt{update()} reads hardware and changes \texttt{read()};
    \item shutdown is idempotent and restores \texttt{INPUT};
    \item destruction releases the claim;
    \item a second owner reports
          \texttt{error() == StatusCode::ResourceBusy};
    \item an invalid pin reports
          \texttt{error() == StatusCode::InvalidPin} without touching hardware.
\end{enumerate}

\textbf{Extend the test:} script HIGH, LOW, HIGH, LOW without elapsed time. Record
the four results. Why must DigitalInput preserve all four?\\[8pt]
\blank{6.8in}

\section{Fault laboratory}

Change one condition at a time, with power removed before each wiring change.
Restore and recheck the exact schematic after every trial.

\begin{tabularx}{\linewidth}{@{}p{0.23\linewidth}p{0.25\linewidth}X@{}}
\toprule
Safe fault & Expected evidence & What the evidence distinguishes\\
\midrule
Disconnect switch-to-GND wire
& always \texttt{Level::High}
& open return path versus a working press\\
Move input configuration from pull-up to floating input
& unstable or environment-dependent level
& defined bias versus a floating conductor; restore immediately\\
Hold switch pressed during reset
& \texttt{Level::Low} after initialization
& startup state is sampled, not assumed\\
Temporarily slow reporting to 500\,ms
& fewer observations, same mapping
& sampling/display rate versus electrical meaning\\
\bottomrule
\end{tabularx}

\warningbox{Do not create faults by shorting an output, supply, or external signal.
The only wiring fault used here is an open connection. A floating-input
demonstration is brief, uses only D22 and the switch, and is restored to pull-up
configuration before continuing.}

\section{Explain the result}

\textbf{Claim:} In one sentence, state whether the pull-up input distinguishes the
two switch states.\\[8pt]
\blank{6.8in}

\textbf{Evidence:} Cite at least three observations, including measured TP-IN
voltage, expected digital level, and the diagnostic output.\\[8pt]
\blank{6.8in}

\textbf{Reasoning:} Use the pull-up and ground paths to explain why LOW means
the switch is pressed in this circuit.\\[8pt]
\blank{6.8in}

\textbf{Limit:} Why do these trials not prove that every brief raw transition is a
deliberate human press? \blank{5.4in}
